# Payment Integration Skill

Detailed guidance for implementing and modifying payment flows. Load this skill when working on payments, webhooks, or entitlements.

## Architecture

Payments are handled through a single Payments adapter interface that abstracts both providers:
- **Xendit**: Indonesia-focused (QRIS, virtual accounts, e-wallets, IDR)
- **Polar MoR**: Global (cards, wallets, worldwide sales tax/VAT handling)

The adapter lives in `packages/infra`. Business logic MUST NOT call provider APIs directly.

Providers MUST charge per-transaction fees only; do not introduce fixed-cost paid dependencies on the critical path.

## Webhook Handlers

Webhook handlers MUST be idempotent. The same webhook delivered twice must not double-apply.

Signature verification MUST happen before JSON parsing:
- Xendit: verify callback token
- Polar: verify webhook secret

Use raw-body verification. Do not parse JSON then verify.

## Entitlements

Premium feature access is gated through the ConfigStore interface, backed by D1.

Flow: webhook → entitlement record in D1 → ConfigStore evaluation → feature access.

Entitlements MUST be checked at the edge, not client-side, to prevent leaking unfinished features.

## Idempotency Keys

Every mutation (create charge, refund, cancel) MUST carry an idempotency key. The key is typically a UUID generated by the client and stored with the request.

## Error Handling

- Network errors: retry with exponential backoff
- Signature mismatch: log at error level, do not retry
- Duplicate webhook: return 200, no-op
- Unknown event type: log at warn level, return 200

## Testing

- Unit tests for adapter logic
- Property tests for webhook idempotency (fast-check)
- BDD tests for full flow: webhook → entitlement → feature flag → UI

## Files

- `packages/infra/payments/` — adapter interface and provider implementations
- `apps/api/src/routes/payments/` — webhook handlers
- `packages/shared-zod/` — payment request/response schemas
