# DSH adapter — dispatching the manager's roles on DSH

The manager skill (`SKILL.md`) is harness-neutral; this file is its **DSH adapter**. Load it only when running the manager loop on DSH. The role files and their model pins live in `.zcode/agents/<role>.md` — the single source of truth for role models on every harness; DSH has no native role agent, so this adapter is thicker than ZCode's: the dispatch prompt is assembled from the role body and the pin is translated by hand.

Evidence class: prompt-assembly, pin routing, worktree behavior and the retired-identity state below were verified against the installed DSH during the #168 manager run (2026-09-27, this machine) and re-checked while writing this adapter — `~/.dsh/settings.yaml` and the repo scripts cited are on disk, and the pin preflight was re-run. Nothing here is stated that the tool surface or a repo script did not establish. Where a rule is genuinely harness-neutral it lives in `SKILL.md`, and this adapter points at it instead of restating it.

- **Spawn — prompt assembly, not a named agent type.** DSH exposes no harness-level `subagent_type`; `subagent` takes a prompt and spawns a generic child. Every dispatch therefore **inlines the role body verbatim** from `.zcode/agents/<role>.md`: a child that did not receive the body does not carry the role's operating contract, and a role-file edit that never reaches a dispatch prompt changes nothing. Assemble the prompt with `bun run dsh:prompt --role <role> --task-file <task.md>` (or `--task "<text>"`) — it strips the frontmatter, emits `## Task` + `## Role definition`, and appends only the per-run authorization a role body does not already carry — then pass its stdout to `subagent` unchanged. Roles: `implementer`, `senior-implementer`, `reviewer`, `fixer`.
- **Dispatch prompt additions (manager's side).** The manager authors the task text (`--task`/`--task-file`) and must state there the per-run facts a role body cannot know: the task, the Definition of Done, that A owns CI green, the worktree path (`.worktrees/<slug>` on branch `agent/<slug>`), and that the role keeps its own plan. The **todo duty** and the **fix-then-re-review trigger** are canonical in `SKILL.md` (step 1 / Reliability & supervision); this adapter does not restate them. Compressed: the todo list is per-session and turn-scoped (never inherited, cleared at each `turn/start`) with whole-list replacement and one `in_progress` item; a fix touching a High finding, an engine seam or a contract forces a scoped re-review of the fix commits before merge.
- **Spawn / continue / results.** `subagent` runs in the background by default and returns a durable agent id immediately; the child's final assistant message arrives as a settle notice, so there is nothing to poll for. Continue a running or idle child with `send_message(agent_id, …)` — a completed child stays resumable, so a red-CI re-dispatch or a stall respawn prefers `send_message` over a new `subagent` unless the child crashed. Do not use `subagent_fork` for a role dispatch: it inherits this conversation, and the role contract must be inlined, not inherited. Read the result from the settle notice, never by re-reading a transcript.
- **Model routing — pin → `provider`/`model`/`reasoning_effort`, by hand, through two gates.** DSH children inherit the session model unless the dispatch names a route. Map the role pin explicitly: take the text after the last `/` in the `model:` value, strip a surrounding quote and any `:cloud` suffix, set `provider: "ollama"`, `model: <id>`, and map `thoughtLevel:` → `reasoning_effort:` (the #168 run mapped `d5585e04-…/deepseek-v4.1-flash:cloud` → `ollama` + `deepseek-v4.1-flash`, `thoughtLevel: max` → `reasoning_effort: max`). A dispatch must clear **two independent gates** on this machine: (1) the provider catalog — `llm-pi-ai.providers.ollama.models` in `~/.dsh/settings.yaml` (five ids; this is what `scripts/dsh-pin-check.mjs --check <id>` probes); and (2) the **subagent dispatch allow-list** — `subagent-model-selection.allowedModels` (`enabled: true`), currently exactly `ollama/deepseek-v4.1-flash`, `deepseek-official/deepseek-flash`, and `ollama/glm-5.3-flash`. `list_subagent_models` reports gate 2 and is **authoritative for what may be dispatched** — a route absent from it cannot be dispatched at all; it is incomplete only about the provider catalog (`kimi-k2.7-code`, `kimi-k3` and `glm-5.3` are declared in that catalog but are not dispatchable routes). A blocked route fails observably with `Error: child LLM route "<provider>/<model>" is not allowed for this Session`. ADR-0005/0023's 2026-08-29 probe recorded that only `workflow`'s one-shot `agent()` accepted a model override; the current DSH tool surface exposes `provider`/`model`/`reasoning_effort` on the continuable `subagent` itself, which is what this adapter uses — those ADR lines describe the older tool surface, not the operative mechanic.
- **A pin with no dispatch route.** ADR-0023 decision 3 holds: a pin that fails to resolve is a **harness-config gap, fixed in the harness's own configuration — never rerouted to a different model**; a per-harness fallback forks the pin truth and makes the run silently weaker than the pin declares. So: (1) if the id is missing from the provider catalog, declare it there (`bun scripts/dsh-pin-check.mjs --fix` appends it — never reroute); (2) if it is in the catalog but missing from `subagent-model-selection.allowedModels`, add the route to that allow-list in `~/.dsh/settings.yaml`; (3) if neither is possible, the pin or the provider must change, recorded in the role file (the single source of truth) — never a silent substitution, and never an uncommitted working-tree pin (the #168 run violated this: it substituted a local pin instead of recording the rule). Verified caveats (2026-09-27): no preflight command exists today — ADR-0023 names `bun run dsh:preflight` and `bun run zcode:preflight`, neither is in `package.json`, and `scripts/zcode-pin-check.mjs` is deleted — and `scripts/dsh-pin-check.mjs`'s per-role parse of the current **quoted** frontmatter `model:` values is buggy: it reads them as `glm-5.3:cloud"` and reports every role ✗, so a per-role `✗` in that block is not a routing failure (check a concrete id with `--check <id>`; all five catalog ids are declared and served). Issue #222 owns restore-vs-annotate for both caveats — neither is a licence to reroute.
- **Worktree convention — the in-repo `.worktrees/<slug>`.** Every DSH bash invocation gets its own `/tmp`, so a worktree under `/tmp` is invisible to the next call and cannot work at all (probe-verified). Dispatch implementer-class roles into `.worktrees/<slug>` on branch `agent/<slug>` — `git worktree add .worktrees/<slug> -b agent/<slug> origin/main`, run from the main checkout — and the fixer reattaches `.worktrees/<slug>`. `.worktrees/` is committed to `.gitignore`; the manager's cleanup duty is `bun run worktree:clean` from the main checkout, which keeps unmerged work and reports first with `--dry-run`. Never write a worktree or scratch state under `/tmp`, and never rely on `.git/info/exclude` — it is local and uncommitted. Canonical rules: `SKILL.md` (Workspace isolation) and `.zcode/agents/README.md`.
- **Review worktree dependencies.** A fresh worktree has no `node_modules`, and workspace symlinks resolve back to the source checkout, so a reviewer in a fresh detached worktree cannot execute the suite (observed on the #168 review of PR #219). Strategy, in order: (1) **diff-only review** when the PR is docs/skill/config-only and needs no execution — state that basis explicitly in the review; (2) for a PR whose verification needs execution, run `bun install` in the review worktree first (slow, but the worktree is then warm) or reuse a named warm worktree. Never claim a test run that did not happen; the reviewer chooses and reports which basis it used.
- **`gh` identity.** Verified by repo state, not by a DSH hook layer: DSH wires no identity hook for this workflow, and this repo's per-role identity machinery (`scripts/role-gh-identity/`, ADR-0025) was **retired in #133** — the directory does not exist on `main` and `.zcode/config.json`'s `PreToolUse` is empty. On DSH every role's `gh` therefore runs under the manager session's ambient identity; no role is denied a bare `gh`, and the manager session is never denied. The dormant deny-redirect design (`gh-as <role> <gh args…>`, opt-in `enabled: false`, fail-open) is history, not an active mechanic — this adapter does not claim it. See `.zcode/agents/README.md` § Role GitHub identities (retired).
- **Approvals and isolation.** This workflow's DSH sessions run with approval prompts disabled and the workspace-write file policy (verified 2026-09-27 in the session that wrote this adapter), so a dispatch, a background job, a commit or a `gh` call needs no per-action approval. Workspace isolation is not harness-provided — it is the role files' worktree rule above, which every dispatch must state.
- **Verifying a dispatch.** A subagent's `todo_write` events land in its DSH session log (`~/.dsh/sessions/<project-slug>/<session-id>/session.v3.jsonl.zstd` on this machine), so the manager verifies the todo duty instead of trusting prose: a log with `todo/write` events and a `todos` projection that moves is the evidence. #168's dispatched subagent listed 28 tools including `todo_write` but logged 0 `todo/write` events — the defect the duty closes.
