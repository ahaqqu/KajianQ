# DSH adapter — dispatching the manager's roles on DSH

Load when running the manager loop on DSH; `SKILL.md` is harness-neutral.

## Spawn

1. **Prompt assembly.** No `subagent_type` exists; `subagent` takes a prompt. Inline the role body verbatim from `.zcode/agents/<role>.md` — a child without it does not carry the role's contract, and a role-file edit that never reaches a dispatch prompt changes nothing. `bun run dsh:prompt --role <role> --task-file <task.md>` (or `--task "<text>"`) strips the frontmatter and emits exactly the section list its header comment documents — that comment is canonical for what the script emits, so read it there rather than restating the list; pass its stdout to `subagent` unchanged. State per-run authorization in the task text; where a role body carries its own `## Dispatch authorization` section, the role contract is canonical in `.zcode/agents/README.md` (Dispatch authorization).
2. **Task text carries:** the task, the Definition of Done, that the implementer owns CI green, the worktree path (`.worktrees/<slug>`, branch `agent/<slug>`), the lock/unlock duty (lock at creation with a reason naming the role and ticket, unlock before reporting done), and that the role keeps its own plan. The **subagent todo duty** and **fix-then-re-review trigger** are canonical in `SKILL.md` (step 1; Reliability & supervision) — state them in the prompt and follow them there.
3. **Continue, don't respawn.** `subagent` runs in the background, returns a durable agent id at once, and delivers the result as a settle notice — read it there, never from a transcript. `send_message(agent_id, …)` continues a running or idle child; a completed child stays resumable, so a red-CI re-dispatch or stall respawn prefers it over a new `subagent` unless the child crashed. Never `subagent_fork` a role dispatch: it inherits the conversation, and the contract must be inlined.
4. **Todo-duty evidence:** `todo_write` events in the subagent's `~/.dsh/sessions/<project-slug>/<session-id>/session.v3.jsonl.zstd` — `todo/write` events and a moving `todos` projection.

## Model routing

- **Pin → route, by hand — while a policy lets a dispatch name one.** A dispatch carries `provider`/`model`/`reasoning_effort` only when the session holds a route-selection policy. With the policy not enabled the delegation tool exposes none of them and rejects one that is supplied (`child model selection is disabled for this tool instance`), so the child inherits the dispatcher's route **and effort**: a pin that differs from the session's route is then not applied, and its `thoughtLevel` is not either. Strip the pin's surrounding double quotes, normalize by shape, then set `provider: "ollama"`, `model: <id>`, `thoughtLevel:` → `reasoning_effort:`. Shapes: `<uuid>/<id>:cloud` → text after the last `/`, minus `:cloud`; `custom:<uuid>:<id>%3Acloud` → last `:`-segment, `%3A` → `:`, minus `:cloud` — the after-the-last-`/` recipe cannot dispatch this shape.
- **The composed catalog is the routing reference.** A pin's model id must be declared in the provider catalog `llm-pi-ai.providers.ollama.models` of the composed profile — the bundles in the profile `package.json`'s `dsh.profile.bundles`, then the profile `cordis.patch.yml`, then `$DSH_HOME/cordis.patch.yml`, each layer replacing an entry's keys wholesale — and the `ollama` adapter rejects an id absent there with `pi-ai provider "ollama" has no configured model "<model>"`. The route policy `subagent-model-selection-settings` is the second check: while it is enabled, its `allowedModels` must carry `ollama/<id>`, so keep it carrying every declared catalog id and change it only as an owner-side settings edit — never per blocked pin.
- **A blocked pin fixes the config, never the model.** Declare the missing id in the provider catalog — in the layer that owns it, never an installed bundle. If that is not possible, the pin or the provider changes — recorded in the role file, never a silent substitution to another model, never an uncommitted working-tree pin. A per-harness fallback forks the pin truth and makes the run silently weaker than the pin declares.
- **Recorded-policy session gotcha.** A pin is expressible only where the session recorded a selection policy; the policy is recorded at composition, inherited by its children, and kept for the session's lifetime. A route outside the recorded list fails with `Error: child LLM route "<provider>/<model>" is not allowed for this Session`, and `list_subagent_models` lists only that recorded list — never the catalog. A settings edit reaches new sessions only: a session that already recorded a policy keeps its own. A session composed while the policy was not enabled records none at all, so inheritance is the only route it can delegate to.
- **Pin check.** `bun run dsh:preflight` (`scripts/dsh-pin-check.mjs`) composes that layer stack itself (never shelling out to `dsh`, whose boot rewrites the profile root) and reads every `.zcode/agents/*.md` pin — quoted or bare, both editor shapes. It fails on a pin whose id is absent from the composed catalog, and on a declared pin whose `ollama/<id>` route is outside an enabled policy's `allowedModels`, printing the exact owner-side edit. With no policy in force it fails any pin that is not the composed `agent-default-model` route — nothing else can be inherited — and notes that a dispatch cannot name the pin's route or `thoughtLevel`; a pin that is that route passes with the inheritance note. Check a concrete id with `--check <id>`. `--fix` declares a missing catalog id in the layer that owns the catalog (the profile patch, or the home layer when it overrides that entry), atomically and behind a timestamped backup beside it; it never edits a bundle layer and never the policy. `DSH_PIN_CHECK_PROFILE_DIR`, `DSH_PIN_CHECK_HOME` and `DSH_PIN_CHECK_INSTALL` — with `DSH_PIN_CHECK_ROLES_DIR` and `DSH_PIN_CHECK_CATALOG` — point the script at a fixture tree, so tests exercise `--fix` against a fixture and never the real files; the three roots are all-or-nothing.

## Workspace

- **In-repo worktrees.** `/tmp` is per-bash-invocation, so a worktree or scratch state there is invisible to the next call. Dispatch implementer-class roles into `.worktrees/<slug>` on branch `agent/<slug>`: `git worktree add .worktrees/<slug> -b agent/<slug> origin/main`, from the main checkout; the fixer reattaches `.worktrees/<slug>`. `.worktrees/` is committed to `.gitignore`. Cleanup: `bun run worktree:clean` from the main checkout, and only with `--no-active-dispatches` (without it every removal a sweep would make is withheld and the run exits non-zero, while a gated run with nothing to remove withholds nothing and exits 0; `--dry-run` reports first and needs no flag); a locked entry is kept with its reason whatever flags are passed, so clear a lock left by a crashed dispatch deliberately with `--unlock <slug>` (repeatable, never sweeps); unmerged work kept. Canonical: `SKILL.md` (Workspace isolation).
- **Review worktree dependencies.** A fresh worktree has no `node_modules`, and workspace symlinks point back to the source checkout, so the suite cannot run there. For a docs/skill/config-only PR, review the diff and state that basis; when verification needs execution, `bun install` in the review worktree or reuse a warm one. Never claim a test run that did not happen.

## Session facts

- **Count live sessions before every dispatch.** The cap is three concurrent sessions with the manager as one of them, so at most two subagents may be live at once — canonical: `SKILL.md` (Concurrency cap). Count with `list_agents` at `scope: descendants` (a grandchild consumes the budget too) and read every entry that is not settled as live: `running` is live, and an `inactive` child still holds its session until it is finished with. A dispatch past the cap does not queue — the provider kills it mid-task, which is how an implementer's committed-but-unpushed work and a QA round's unposted verdict are lost.
- **`gh` runs under the manager session's ambient identity** — no identity hook is wired, no role is denied a bare `gh`, and the manager session is never denied. The `project` scope rides that ambient token; when it is absent, `gh project` fails closed with `missing required scopes [read:project]`, and only the owner can land the interactive refresh (`gh auth refresh -s project`). Failure mode and the loop's response: `SKILL.md` (Board API mechanics).
- **`gh` log reads need a writable cache.** `~/.cache/gh` is read-only under the workspace-write policy, so `gh run view <run> --log-failed` fails with `failed to get run log: … read-only file system`; export `XDG_CACHE_HOME` to a writable path inside the same command before reading a log.
- **Long mechanical jobs are background jobs.** A board-wide re-application pass or any `gh` loop longer than one command budget runs as a background bash job (`run_in_background: true`), read with `job_output` — never a foreground call. The pass's mapping-file and complete-read rules are harness-neutral: `SKILL.md` (Board API mechanics).
- **Approvals disabled, workspace-write policy** — a dispatch, a background job, a commit or a `gh` call needs no per-action approval. Isolation is not harness-provided: it is the role files' worktree rule, which every dispatch must state.
