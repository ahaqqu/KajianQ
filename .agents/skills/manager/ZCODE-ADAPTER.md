# ZCode adapter — dispatching the manager's roles on ZCode

The manager skill (`SKILL.md`) is harness-neutral; this file is its **ZCode adapter**. Load it only when running the manager loop on ZCode. The role files and their model pins live in `.zcode/agents/<role>.md` — the single source of truth for role models on every harness; on ZCode the harness parses them natively, so the adapter is thin.

Mechanics per ZCode's native behavior.

- **Spawn:** each role is a named `subagent_type` (`implementer`, `senior-implementer`, `reviewer`, `fixer`, `qa`) defined in `.zcode/agents/`, dispatched with background run. The definitions and model pins resolve automatically — no prompt assembly or role-body inlining needed. The `qa` role takes no worktree: it is read-only on the repo and probes the deployed staging environment.
- **Resume:** continue a child with `SendMessage` (manager steps 2 and 5); re-issue its prompt verbatim when respawning after a stall.
- **Results:** read a child's report from its final message. A completed background agent's `output.txt`/`task.output` artifact holds the final message text, while the full run history sits in a much larger `transcript.jsonl` beside it — do not read the transcript for the result or you will overflow your context.
- **Model routing:** handled by ZCode — the `model:` frontmatter ref in each role file resolves through the client's provider config (`~/.zcode/v2/config.json`, `provider` object). A pin that does not resolve fails the spawn with "Model provider is not configured: <id>"; fix it in the client's provider settings, not the role file. Pin changes reach new spawns only after a client restart. Override order: `~/.zcode/agents/<role>.md` (user) → this project's `.zcode/agents/`. A model-pinned dispatch keeps `SendMessage` continuation. The `fixer` reuses the implementer worktree (`.worktrees/<slug>`) or adds a fresh one from the existing branch (`git worktree add .worktrees/<slug> agent/<slug>` — no `-b`).
- **Dispatch note:** ZCode resolves a named role natively, so the dispatch prompt carries only the manager's per-run facts — but it must still state the task, the Definition of Done, that A owns CI green, the worktree path (`.worktrees/<slug>` on branch `agent/<slug>`, never `/tmp` or `.wt/`), the lock/unlock duty (lock at creation with a reason naming the role and ticket, unlock before reporting done), the **todo duty**, and the **fix-then-re-review trigger** — both canonical in `SKILL.md` (step 1; Reliability & supervision); state them in the prompt and follow them there.
- **Approvals and isolation:** approvals need no inlining on ZCode — the role files are parsed natively; workspace isolation is the role files' own rule, canonical in `.zcode/agents/README.md` (Dispatch authorization, Workspace isolation) and `SKILL.md` (Workspace isolation).
