# ZCode adapter — dispatching the manager's roles on ZCode

The manager skill (`SKILL.md`) is harness-neutral; this file is its **ZCode adapter** — the reference harness this workflow was designed for. Load it only when running the manager loop on ZCode. The role files and their model pins live in `.zcode/agents/<role>.md` — the single source of truth for role models on every harness; on ZCode the harness parses them natively, so the adapter is thin.

Mechanics per ZCode's native behavior. Evidence class: spawn/resume/result mechanics verified by live probes on the installed client (2026-08-30, this repo); pin resolution is **config-dependent, not verified by the probes** — see Model routing and ADR-0005's known-gap note. Child pin resolution under a worktree parent is a separate cwd-based failure mode, observed in a real worktree child dispatch — see "The worktree role-pin trap" below.

- **Spawn:** each role is a named `subagent_type` (`implementer`, `senior-implementer`, `reviewer`, `assistant-manager`) defined in `.zcode/agents/`, dispatched with background run. The definitions and model pins resolve automatically — no prompt assembly or role-body inlining needed.
- **Resume:** continue a child with `SendMessage` (manager steps 2 and 5); re-issue its prompt verbatim when respawning after a stall.
- **Results:** read a child's report from its final message. Probe-verified (2026-08-30): a completed background agent's `output.txt`/`task.output` artifact holds the final message text, while the full run history sits in a much larger `transcript.jsonl` beside it — do not read the transcript for the result or you will overflow your context.
- **Model routing:** the `model:` frontmatter ref must name a provider **key** in the ZCode client's provider config (`~/.zcode/v2/config.json`, `provider` object). The template pins every role to the caching channel `builtin:zai-start-plan/GLM-5.3-Flash` (issue #125) — a pin resolves only if a provider entry is keyed `builtin:zai-start-plan` in that file; a key mismatch fails the spawn with "Model provider is not configured: <id>" (reproduced live 2026-08-30 — see ADR-0005's known-gap note). Before a model-pinned run, verify resolution with `bun run zcode:preflight`: machinery violations (missing wiring/pins) exit non-zero, while a pin that does not resolve in the local provider config is a visible drift warning (CI has no client config) — treat a warning as a pre-dispatch blocker all the same. Pin changes — committed or user-scope — reach new spawns only after a client restart. Override order: `~/.zcode/agents/<role>.md` (user) → this project's `.zcode/agents/` → template pin (see the pinned-defaults table in the role registry). A model-pinned dispatch keeps `SendMessage` continuation.
- **Approvals and isolation:** subagent approval and workspace-isolation mechanics follow the `subagent` skill (§ Workspace isolation) — it is harness-neutral by design.

## The worktree role-pin trap (child spawns resolve from the parent's cwd)

Role definitions for a child spawn resolve from the **parent subagent's working directory**, not the session workspace's. When a role subagent runs in a git worktree (per § Workspace isolation), its role-typed child spawns (`subagent_type: reviewer`, the sub-reviewers, …) resolve `.zcode/agents/<role>.md` **inside the worktree** — and a fresh worktree carries only the branch's **committed** pins. Any uncommitted pin override that exists only in the session workspace's tree (a local provider-key fix, a temporarily patched `model:` line) does not exist there. If the committed pins name a provider key absent from the client's provider config (`~/.zcode/v2/config.json`), **every** role-typed child spawn fails with "Model provider is not configured: <id>" — and the parent has no visible cause, because the failure surfaces only as the child spawn error, far from the config that explains it. Measured cost (issue #110, 2026-08-30): ~25 wasted probe calls and two failed manager spawns in one run.

Detect it before dispatching: run `bun run zcode:preflight` **from inside the worktree** — the preflight script resolves `.zcode/agents/` from its own location, so it checks the worktree's committed pins against the same client config and exits non-zero on any machinery violation (a non-resolving pin surfaces as a drift warning with the exact fix) before a single probe is spent. Since issue #125 the committed pins are concrete on the caching channel, so the trap now fires only when the local provider config lacks the pinned provider key — the preflight says exactly that.

The two sanctioned workarounds for worktree-based dispatches:

- **(a) Patch the worktree's pins, uncommitted.** Copy the working pins from the session workspace into the worktree's `.zcode/agents/<role>.md` but never commit them — revert before committing anything else, so the branch keeps the template pins (ADR-0005 decision 3: a resolution failure is a config gap, never a reason to change committed pins).
- **(b) Dispatch a role-less default child.** A generic `subagent` with no role `subagent_type` skips role-file resolution entirely and inherits the session model (mechanics per ADR-0005's DSH probes; not yet probe-verified on ZCode — verify on first use and record the dispatch in ADR-0005). When persona fidelity matters, carry the role body in the prompt the way the DSH adapter does (`bun run dsh:prompt --role <role>`, DSH-ADAPTER.md § Dispatch recipe) — the definition then travels from the dispatcher, not from the child's cwd.

Do not "fix" the trap by committing the local provider-key workaround to the branch or by rerouting pins to whatever the worktree resolves — both fork the pin truth ADR-0005 names as the single source.
