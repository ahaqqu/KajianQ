# Bug retrospectives

A bug that **reached a state the workflow calls good** — merged work, an accepted ticket, a defect the QA role or the owner filed, a red post-merge run — is an **escaped defect**, and it gets a **retrospective on why it happened**. The boundary is one test: _did the round catch it before that state?_ A review finding on the open PR is the case on the other side — the review pass caught it while the change was still in review — so it needs its fix and no retrospective: there is no "why did this pass?" to answer. You run the retrospective when the find lands; the escaped defect's own fix goes through the normal implement → review loop beside it, but the round is not summarized until the retrospective is recorded. A fix closes the symptom, and the retrospective asks why the plan, the tests, the review or the gate did not catch it — because a class that survives its fix returns as the next ticket.

The duty is **proportional, never optional**. Record it as a comment on the defect's own ticket — file one if the find has none, because a bug worth a retrospective is worth a ticket — and carry it into step 6's summary. It answers four things:

1. **The class, and whether it recurs.** Name the class from the code path that failed rather than from the ticket title, and state it on a `Class: <name>` line so the next round can find it. Answer recurrence from evidence, not memory: `gh search issues --repo <owner>/<repo> --match comments 'Class: <name>'` returns that class's candidate records, and `gh search issues --repo <owner>/<repo> --match comments 'Bug retrospective'` returns every retrospective recorded so far — read the `Class:` line off each hit and count the ones sharing this class, prior rounds only: exclude this round's record and the ticket it lands on, or run the query before you post. Report this round's count, the prior instances, the query you ran, and "no prior instance" when there are none. Quote the query whole and shell-quoted — the marker is the query, never a phrase inside it (`'"Class:"'` is a hard `Invalid search query`) — and search the `Class:` form rather than a bare class name, which collides with ordinary prose (`coupling`). The individual defect is not the signal; a repeating class is. Classes seen so far — **unearned coverage**: a claim of exhaustiveness (every category, every source, every rule) carried by a hand-written list instead of by construction, so the missing member is invisible; **overloaded flag**: one value carrying two meanings, so the guard written for one meaning is skipped by the other; **coupling**: a policy decision (what we spend) gating a guarantee (what we must compute); **single sample**: a verdict read off one nondeterministic observation, where the outcome flips on a branch the change does not control. The list is open — a defect that fits none of them gets a new class name, never a nearest match.
2. **The earliest point that could have caught it**, named concretely: the ticket's acceptance criteria and routing labels (`to-tickets`), the design or spec (`grill-with-docs`, `to-spec`, `plan-review`), the test intent (`writing-tests`, `guided-implementation`), the review pass (`code-review`), or the gate (`packages/eval`, the smoke selection, a CI check).
3. **The workflow change that would catch the class there.** A change names the file that gains the rule, the suite that gains the case, or the gate that gains the check — "test more carefully next time" is not a change. `no workflow change: <reason>` is the other outcome, and it carries the same bar: the reason names the existing rule that already covers this class, as `file:line`, and the record states which of the three outcomes the round took — `covered by <file:line>`, `gap — landed as <PR>`, or `<owner decision: …>` for a change that alters what an agent is. "The workflow already covers this" is a claim you can be wrong about, and the reviewer can check it.
4. **Where it lands, and who authors it.** The owning skill, role file or gate, filed as its own PR — dispatched through step 1 to the implementer role in its own `.worktrees/<slug>` on `agent/<slug>`, and reviewed at step 3 at the depth its diff determines. A retrospective's change is an ordinary PR: prose rather than runtime code does not exempt it from review, and it holds one of the two live dispatch slots until it settles, with its worktree joining step 6's cleanup like A's. It forces no scoped re-review of the fix PR it rides beside (Fix-then-re-review). One that changes **what an agent is** — a role file, this loop, or a gate's pass/fail meaning — goes to the owner as a decision instead of being landed, and the round records it as `<owner decision: …>`.
