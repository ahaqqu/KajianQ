# ADR-0023: Role-agent model pins are the single source of truth, honored per harness

## Status

Accepted (2026-08-29). Records the model-routing decision for the manager-orchestrated agentic workflow (#96, PR #98). Builds on ADR-0009 (price weighed in every model decision) and the template-sync ownership rules in `template-sync.json`. **This is the canonical record**; the template-heritage near-duplicate [`adr/0005-role-model-pins-honored-per-harness.md`](0005-role-model-pins-honored-per-harness.md) is marked superseded in its favour.

## Context

The manager skill (`.agents/skills/manager/SKILL.md`) dispatches the role agents defined in `.zcode/agents/*.md` — four today (`implementer`, `senior-implementer`, `fixer`, `reviewer`); the original decision and its 2026-08-29/30 probes were made against six — each with a `model:` pin in its frontmatter. The repo runs two harnesses: **ZCode**, which parses those files natively and resolves pins through its override order, and **DSH (DeepSeek Harness)**, which parses none of them.

Verified against the installed DSH (probes 2026-08-29, re-probed 2026-09-27): the continuable `subagent` tool takes `provider` / `model` / `reasoning_effort` directly, so a route-named dispatch is continuable — a `send_message` follow-up reaches the same child, which is how the #168 and #220 manager runs dispatched pinned roles and continued them — while a bare `subagent` inherits the session model; `subagent` has no `subagent_type`, so the role body is inlined in the prompt. The `workflow` tool's one-shot `agent(prompt, { provider, model })` override remains for fan-out, where one-shot children are the right shape; nested spawns work from both plain-subagent and workflow children, so the reviewer can dispatch its two sub-reviewers from either. An initial probe round showed `glm-5.3` failing on DSH while ids declared in the DSH provider's model list dispatched — root cause was a missing declaration, not an upstream gap: ollama.com serves `glm-5.3` (catalog-verified), and after declaring it in `~/.dsh/settings.yaml` (hot-reloaded) the pin routes. Every template pin now dispatches on DSH. Issue #96's earlier non-goal ("no changes to the pinned role models") predates this owner request to make DSH work for every ZCode-configured role.

**Known gap — ZCode-side pin resolution (recorded 2026-08-30, from PR #98's review).** On ZCode the pin's provider id must match a provider **key** in the client's provider config (`~/.zcode/v2/config.json`). This machine's ollama provider was keyed by its client-generated UUID, so _every_ pinned role failed to spawn with "Model provider is not configured: ollama" — reproduced live for all six roles during the PR #98 review (which is how the review's thermo sub-reviewer passes reached the fallback `thermos-with-comments` already allows). The config was fixed by adding an `ollama`-keyed provider entry carrying the same baseURL/models (the client's spawn-time registry is cached from startup, so a mid-session fix needs a client restart to take effect — restart-verification pending). The gap motivated a ZCode-side preflight gate mirroring the DSH one: it checked every role pin's provider key and model id against the client's provider config and exited non-zero with the exact config fix, reading the config file only (no writes: the entry carries credentials and the client owns its keying) and unable to verify the running client's startup cache. That gate was retired on 2026-09-01 (PR #130) — the ZCode editor began rewriting role files on save, so a static machinery gate hard-failed every edited role — and ADR-0024 records the ruling; ZCode pin health surfaces at dispatch instead, as "Model provider is not configured: `<id>`" (`.agents/skills/manager/ZCODE-ADAPTER.md`).

## Decision

1. **`.zcode/agents/<role>.md` frontmatter `model:` is the single source of truth for role models on every harness.** Model identity is never duplicated into skills, prompts, or per-harness role variants. The _mechanism_ of honoring a pin is per-harness; the _value_ travels from one file.
2. **Every harness honors the pin.** ZCode does so natively (override order: user → project pin → template default; adapter: `.agents/skills/manager/ZCODE-ADAPTER.md`). DSH does so through its adapter (`.agents/skills/manager/DSH-ADAPTER.md`): at dispatch, read the pin, normalize it to the bare id, and call the continuable `subagent` with `provider: "ollama"`, `model: <id>`, and `thoughtLevel:` → `reasoning_effort:` — the same tool a follow-up `send_message` reaches, so a route-named dispatch is never forced one-shot; a bare `subagent` (no route) inherits the session model. `workflow`'s one-shot `agent()` remains for fan-out, where one-shot children are the shape.
3. **A pin that fails to resolve on a harness is a harness-config gap, fixed in the harness's own configuration — never rerouted to a different model.** On DSH the fix ships as a script, not wording: the preflight gate `bun run dsh:preflight` (`scripts/dsh-pin-check.mjs`) reads every role pin from `.zcode/agents/` — quoted or bare, in either shape the ZCode editor writes — and checks **two** gates in `~/.dsh/settings.yaml`: the id is declared in the provider catalog `llm-pi-ai.providers.ollama.models` and served by ollama.com, and its `ollama/<id>` route appears in `subagent-model-selection.allowedModels`. The second is a **narrowing guard**, not a filter: the route list carries every declared catalog id, so it rejects nothing today and exists to catch a future narrowing — and because the list is recorded per session at composition and inherited by its children, a settings edit reaches new sessions only, while the script can read the configured list but never a session's recorded one. The gate exits non-zero with the exact fix for each failure — for a narrowed route, the `allowedModels` entry to add. `--fix` appends missing catalog declarations only — atomically, with a timestamped backup, only for ids the catalog serves (an unserved id is a pin/provider change, never a declaration) — and never touches the route list, whose narrowing is an owner-side settings decision. On ZCode the equivalent preflight is retired (2026-09-01, PR #130; ruling recorded in ADR-0024): pin health surfaces at dispatch as "Model provider is not configured: `<id>`". Per-harness fallback models are rejected: they fork the pin truth, make the run silently weaker than the pin declares, and bury the deviation inside skills. The role files keep their template pins untouched (template-sync conflicts avoided). Skill and adapter files record no fallback tables — the _absence_ of routing deviations is the invariant; the gates' exit codes are the check, and probe evidence and dates live in this ADR and the PR, not in skills.
4. **Cost discipline (ADR-0009) holds:** all ids stay on the existing ollama provider on the current Pro plan — no new vendor, no free-tier routing of anything sensitive.

**Update (2026-09-27, role-pin refresh — owner-pinned values; supersedes decision 3's "the role files keep their template pins untouched" for the current pin set, not the decision).** Three `.zcode/agents/` pins changed, each moving `thoughtLevel` to `max`: `fixer` `glm-5.3-flash` → `deepseek-v4.1-flash`; `reviewer` `kimi-k2.7-code` → `glm-5.3-flash`; `senior-implementer` `glm-5.3` → `deepseek-v4.1-flash` (`implementer` unchanged at `deepseek-v4.1-flash`). The retired `reviewer` and `senior-implementer` ids (`kimi-k2.7-code`, `glm-5.3`) were declared in the DSH provider catalog (`llm-pi-ai.providers.ollama.models`) but absent from the hard subagent dispatch allow-list (`subagent-model-selection.allowedModels`), so they could not dispatch; the owner re-pinned instead of extending that allow-list (the allow-list was not edited), and `fixer`'s retired id (`glm-5.3-flash`) was dispatchable, making its move a plain re-pin. All four role pins were re-probed dispatchable on DSH under this ADR's revisit trigger: decoded per `.agents/skills/manager/DSH-ADAPTER.md` (both the `<uuid>/<id>:cloud` and `custom:<uuid>:<id>%3Acloud` shapes) to `deepseek-v4.1-flash` (fixer, senior-implementer, implementer) and `glm-5.3-flash` (reviewer) — both present in the allow-list, reported by `list_subagent_models`, checked "declared, served" by `bun scripts/dsh-pin-check.mjs --check <id>`, and confirmed by live `subagent` probes at `reasoning_effort: max`.

**Update (2026-09-27, gate restoration — issue #222; the operative record for decision 3).** The DSH preflight had been left unreferenced when #133 (`11af293`) removed `dsh:preflight` from `package.json`, and three defects had made it useless: `readPin` returned quoted values verbatim, so every role reported `✗`; the gate checked only the provider catalog, so it certified pins that the session's route list rejects (`Error: child LLM route "ollama/<id>" is not allowed for this Session`); and there was no test. The gate is restored: `bun run dsh:preflight` is back, quotes and both pin shapes (`<uuid>/<id>:cloud`, `custom:<uuid>:<id>%3Acloud`) normalize to one id, the `subagent-model-selection.allowedModels` route is the second check, and `tests/scripts/dsh-pin-check.test.mjs` pins all of it against fixtures — `DSH_PIN_CHECK_SETTINGS`, `DSH_PIN_CHECK_ROLES_DIR`, and `DSH_PIN_CHECK_CATALOG` override the machine-global settings file, the roles directory, and the ollama.com fetch, so `--fix` is exercised against a fixture and never against this machine's `~/.dsh/settings.yaml`. The ZCode-side gate stays retired (ADR-0024). The route list was restored by the owner carrying every declared catalog id (issue #222's scope update); the curated subset it briefly held was the obstacle, not the mechanism, because disabling the policy removes model selection entirely — no `provider`/`model`/`reasoning_effort` on `subagent` — so it cannot be used to free a pin.

## Consequences

- All four ZCode-configured roles run end-to-end on DSH with **their exact pinned models** — re-probed on 2026-09-27 and checked by `bun run dsh:preflight` against the provider catalog and the route list; the DSH adapter documents no routing deviations. On ZCode, pin resolution is config-dependent (see the known-gap note in Context): the `ollama`-keyed provider entry fix was the remedy, the preflight that once verified it is retired (ADR-0024), and a ZCode run relies on dispatch-time resolution — "Model provider is not configured: `<id>`" — before the "every pinned role" claim is made.
- Model changes remain one-file edits: change a pin and re-probe the new id on each harness before the next manager run (`bun run dsh:preflight` for DSH); a failure is fixed by declaring the id — and keeping `subagent-model-selection.allowedModels` carrying every declared catalog id — in harness config, in the same change.
- Route-named dispatches are continuable on `subagent`; only `workflow`-fanned-out children are one-shot, and the manager compensates by respawning fresh with logs, so continuation is never silently lost — it changes form per dispatch type.
- Skills carry no routing status, fallback tables, or support-status sections that can go stale; their only routing claim is the dispatch rule and the config-fix procedure.

## Revisit triggers

- A role pin changes in `.zcode/agents/`: re-probe the new id on both harnesses before the next manager run; if it fails to resolve, declare the id (DSH) or fix the provider key/model list (ZCode) rather than rerouting. Run `bun run dsh:preflight` before the pin change reaches a manager run.
- A harness upgrade changes model-resolution behavior: re-run the probe suite (spawn, continuation, nested-from-workflow, per-pin routing) before trusting the loop.
- A third harness is adopted: give it an adapter file in the manager skill, its own pin-honoring rule, and its own preflight gate — the pin file does not move.
