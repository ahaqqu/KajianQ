## 1. Vision & Objectives

### 1.1 What this is

- **KajianQ** — an open-source (MIT) Islamic classical-knowledge chatbot for the **general Indonesian Muslim public** (not scholars), chatting in **Indonesian and English** over a corpus of **original Arabic sources**: Quran (Uthmani), hadith (with sanad & grades), and **pre-600 H kitab** (fiqh, aqidah, tasawuf, history).
- **DARS** (_Dynamic Automated RAG Solution_; evokes Arabic _dars_, "lesson") — the generic, domain-agnostic RAG engine underneath: ingestion, Smart Router, retrieval, generation, evaluation. Engine code contains **no Islamic-domain logic**; KajianQ is a domain pack + apps on top.

Both live in **one monorepo** (ADR-0005): DARS as workspace packages under `packages/`, KajianQ under `apps/`. Reusability (public-service chat, internal-company knowledge) is a stated long-term goal, enforced by package boundaries — not by building a platform prematurely.

### 1.2 Long-term mission

Improve the Islamic character (_akhlak_) of Indonesian Muslims — youth in particular — by making it easy to get answers grounded in classical Islamic sources. The v1 product serves the **general public**; the youth mission is served through accessibility (plain Indonesian, mobile-first PWA), not by narrowing the audience.

### 1.3 Success for v1

**Real public users at small scale.** The product is deployed, open-source, and used by real people. Success = users receive trustworthy, strictly-sourced answers, and the system visibly improves through user feedback. This justifies the traceability, feedback, and evaluation infrastructure being in scope for v1.

### 1.4 Differentiators (moat)

| Feature         | Typical market         | KajianQ                                                                   |
| --------------- | ---------------------- | ------------------------------------------------------------------------- |
| Sources         | Quran + Bukhari/Muslim | + pre-600 H kitab (Mudawwanah, Al-Umm, Ihya, Tabari, …)                   |
| Corpus language | Modern translations    | Original Arabic + labeled machine translation                             |
| Chat language   | English/Arabic-first   | **Indonesian-first** + English                                            |
| Citations       | Partial                | Strict: QS Surah:Ayah · HR Book No. (Grade) · Kitab, Author, Vol:Page:Bab |
| Madzhab         | Opaque                 | Filter/compare; Syafi'i-weighted with transparent gaps                    |
| Reasoning       | Naive RAG              | Principle-aware: general maxims retrieved alongside rulings               |
| Transparency    | Black box              | **Full user-facing Trace** of how each answer was built                   |
| Data quality    | Raw import             | LLM-cleaned, LLM-translated, harness-validated                            |

### 1.5 Hard boundaries (never cross)

1. **Never issue personal fatwa.** The system presents what classical sources say, with citations, and always ends with: _"Untuk fatwa spesifik, silakan konsultasi ulama setempat."_
2. **Never answer beyond the retrieved context.** If retrieval is insufficient, say so explicitly.
3. **Never hide the machinery.** Every answer carries its full Trace (ADR-0007).
4. **Never silently machine-translate.** All kitab translations are labeled _"Terjemahan mesin — lihat teks Arab asli"_ with the Arabic always shown (ADR-0006).
5. **Dhaif hadith is always flagged** with a warning.
6. **Never derive a new ruling.** The Generator surfaces classical reasoning (ta'lil, madzhab disagreement, applied Principles) _as cited_; it never synthesizes novel rulings, never resolves disagreements, never upgrades a grade. Insufficient evidence → refusal, not synthesis (ADR-0015).
7. **No corpus-wide inferred knowledge graphs.** Knowledge layers are bounded, curated, human-reviewed concept structures (#24 terminology graph, #29 isnad, Principle Index, curated `concept_links`) — never a community-GraphRAG corpus extraction (ADR-0016).

## 2. Product Specification

### 2.1 Capabilities

- **Bilingual chat (ID/EN)** with automatic language detection; answers in the user's language; Arabic originals shown for every quoted ayah/hadith/kitab passage.
- **Strict citations** — Quran: `QS. Al-Baqarah:255`; Hadith: `HR. Bukhari no. 573 (Sahih)`; Kitab: `Al-Umm, Imam Syafi'i, Jilid 1, Hal. 102, Bab …`.
- **Madzhab policy (Syafi'i-weighted, transparent gaps).** Corpus ingests all madhhabs available. When the user does not specify: lead with the Syafi'i view (Indonesian majority), note other madzhab views _if the corpus covers them_, otherwise state _"pendapat madzhab lain belum tersedia dalam korpus"_. Users may set a madzhab preference or explicitly compare madhhabs. Differences are presented neutrally — never attacking any school.
- **Hadith grade transparency.** Grades (`mutawatir | sahih | hasan | dhaif`) are always displayed; dhaif material carries a warning.
- **Principle-aware answers.** Why/analogy questions retrieve **Principles** (yusr, rahmah, masyaqqah, dharar, umum al-balwa, istihsan, sadd al-dhara'i, …) alongside specific rulings, so answers explain the _lens_, not just the rule.
- **Full Trace panel (user-facing).** Every answer expands to show: router intent, sub-queries, retrieved chunks with scores, model identity. General users see a readable "sources consulted" view first; technical details one tap deeper.
- **Trace-anchored feedback.** Thumbs up/down per answer, plus flagging a specific Trace element: _wrong citation · irrelevant chunk · bad machine translation · questionable grade_. Free-text optional. Anonymous (template's anonymous sessions), rate-limited. Feedback lands in the admin review queue; accepted items become **Golden Set** cases. **Implemented (#13):** `POST /v1/feedback` (store-only wiring, guarded by the anonymous Bearer session, metered by the shared /v1 limiter, ADR-0041) takes one feedback shape per request — a thumb (`rating: up|down`) or a flag (`anchor`) — with the category pinned to its element class in the shared contract (a malformed pairing fails the parse). The route resolves the answer's persisted trace through `RagStore.getAnswerFeedbackTarget` (by the trace's `message_id` or a rehydrated chat row id — both uuids) and rejects a flag whose anchor the trace does not ground with 422: chunk ids against the retrieval refs, citation/translation/grade labels against the re-derived citations frame (and a translation/grade flag additionally requires the cited sheet to carry that layer). Rows carry the user id, so the anonymous self-deletion cascade erases them (ADR-0007). The PWA affordances: anonymous thumbs bar per answer, a flag button per Trace-panel source row, and flag buttons in the citation sheet footer — ids-first externalized copy; anchored flags are recorded with rating −1.
- **Chat history & context awareness** (Postgres-backed sessions).

### 2.2 Quality & safety policy (risk-tiered review)

| Grade flag                                 | Always                                                                    | Deterministic: dhaif/missing grade → warning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Contradiction handler                      | Always                                                                    | Conflicting madzhab sources → present both neutrally                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Faithfulness review (LLM, escalation tier) | ~10% live sample + **all** thumbs-down + full Golden Set pre-release      | Every answer is screened by the deterministic citation validator and the **decision-model pre-gate** (ADR-0042, #168); the reviewer LLM is the **escalation tier** — it runs when the pre-gate doubts a citation, cannot read an answer, fails, or finds nothing to judge — and grades the generator's draft against the retrieved evidence. **Same-vendor since the 2026-09-21 owner decision** (ADR-0044 decision 7); the deterministic citation validator, not vendor separation, carries the invariant                                                                                          |
| Ingestion spot-check (cross-vendor LLM)    | 5–10% of cleaned/translated chunks                                        | Different vendor than the cleaner/translator                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

"Workflow green" is not a verdict |

**Authority order** (per _kaidah ushul_): Quran → Hadith (mutawatir > sahih > hasan; dhaif flagged) → Tafsir → Kitab. Principles are assembled _first in the prompt_ as a lens (presentation order), while the system prompt enforces the Quran-first _authority_ order — the two orderings are deliberately distinct.

The trace-anchored feedback widget remains a future ticket. **Implemented (About + Collection pages):** two public static routes join the chat — `/about` (mission, three working principles, privacy posture; ADR-0017 anonymous local-first stakes) and `/collection` (the source register). ## 3. Architecture

### 3.1 Monorepo (fork of `agentic-project-template`)

One GitHub repo, Bun workspaces. Mechanical template-sync has been retired: the
fork had drifted far enough that every sync produced hand-resolved conflicts, so
unvetted upstream changes were more dangerous than useful, and every file is now
project-owned. `packages/` remains the shared-engine merge path for any future
DARS extraction; `apps/` and `package.json` are project composition. ADRs live in
root `adr/` per project convention.

```
apps/
  web/        # React PWA: KajianQ chat UI (+ admin routes, v1)     — from template shell
  api/        # Hono Worker: /v1/chat, /v1/feedback, /v1/admin/*    — from template shell
packages/
  contracts/  # Valibot contracts for all API boundaries            — template pattern
  infra/      # Logger, ConfigStore, ObjectStore,                  — template adapters
              # RagStore (ADR-0008), + Provider adapters
  rag-core/   # DARS: pipeline interfaces — Router, Retriever,      — NEW, domain-agnostic
              # Assembler, Generator, Reviewer
  rag-ingest/ # DARS: source parsers (Tanzil, hadith-json, Shamela),— NEW, domain-agnostic
              # cleaning/translation pipeline, chunking
  eval/       # DARS: benchmark harness, Golden Set runner, judges  — NEW, domain-agnostic
  rate/       # @app/rate: RateLimiter adapter (process-wide    — shared, project-agnostic
              # in-memory, bounded)
  hardening/  # @app/hardening: security headers/CSP + static    — shared, project-agnostic
              # asset serving for the Hono catch-all
  kajianq-domain/ # KajianQ: madzhab enums, principle seed data,    — NEW, the domain pack
              # prompts (ID/EN), citation formatters
scripts/      # Ingestion & eval CLI (Bun, run off-Workers)
```

**Dropped from template:** `packages/local-first` (no offline requirement — chat needs network anyway), D1 + Notes tracer feature. **Reused as-is:** anonymous-session auth (matches anonymous feedback), Valibot contracts, adapters, i18n, Vitest/fast-check/Playwright-BDD, CI gates (size-limit, agentic-limits; the template's truth gate was removed with template-sync, its check subsumed by `bun run boundary`). The template's Workers deploy pipeline was **not** kept: ADR-0044 replaced it with the VPS deployer (the "topology as code" idea stands; the Cloudflare implementation does not).

**Stage communication:** in-process typed interfaces between packages (modular monolith) — no HTTP between pipeline stages. Per notes.md: simple and maintainable wins; extract a service only when a second consumer actually appears.

**Composition & effect runtime (ADR-0027):** engine packages (`rag-core`, `rag-ingest`, `eval`) and `apps/api` adopt Effect (v4, `effect@4.0.0-rc.112` pinned workspace-wide — the root `overrides.effect` forces a single version and `scripts/check-effect-pin.mjs` fails `bun run lint` if `bun.lock` resolves any other; see ADR-0027 Appendix C) as the typed effect runtime — seam signatures return `Effect<A, E, R>`, `RunContext` maps to tagged services, `runPipeline` owns a `Scope`, provider fallback uses `Effect.retry` schedules, and SSE deltas are `Stream` with interruption propagation. The persistence seams are Effect-signatured too (ADR-0027 decision 7): `RagStore`/`ObjectStore` return `Effect<A, StoreError, R>` with the closed-kind `StoreError` taxonomy (defined in `@app/rag-core`, re-exported by `@app/infra`), and store resources release via `Scope`. The HTTP edge stays Hono + hono-openapi (`Effect.runPromise` bridge), valibot remains the only schema vocabulary (Effect Schema is not adopted), and the frontend stays plain TypeScript (React Query + valibot) — Effect is never exposed over the API contract. Permanently outside the Effect surface: `packages/contracts`, `packages/rate`, `packages/hardening`, migrations + migration CLI, and `provision/vps/deploy/deploy.sh` (each with a recorded reason and reopen condition in ADR-0027 decision 7). Gate: the Workers-runtime spike (bundle size, cold start, tsgo typecheck) must pass before the migration PRs land.

**Fork guardrail amendment (ADR-0009):** the template's "never add paid services to the critical path" is amended — paid LLM/embedding APIs _are_ the critical path of a RAG product. Price must be weighed in every model decision; cost is traced per query; free tiers are used where quality allows.

### 3.2 Runtime topology (ADR-0008)

**Target topology (ADR-0044, 2026-09-20; the repo-side serving path is live on the box, and the operator's manual is [`docs/VPS-OPERATIONS.md`](docs/VPS-OPERATIONS.md), and corpus ingestion is its own runbook ([`docs/CORPUS-INGEST.md`](docs/CORPUS-INGEST.md)); the executed cutover is [`docs/VPS-CUTOVER-RECORD.md`](docs/VPS-CUTOVER-RECORD.md)):**

```
User → Cloudflare DNS           (DNS-only; the CDN proxy must stay OFF — ADR-0044 d4)
         ▼
       netcup VPS, Germany/EU   (nginx reverse proxy → apps/api as a plain Bun process)
         ├─ apps/web             (static build, served by nginx)
         ├─ Postgres + pgvector  (RagStore adapter over pg/TCP — same schema, self-hosted)
         ├─ systemd: kajianq-api (serving), kajianq-cron (03:17 session reclaim)
         └─ encrypted backups + logrotate (14-day access-log retention, ADR-0043)
       Cloudflare R2            (ObjectStore adapter — raw corpus, snapshot dumps)
External APIs: Gemini (free + paid terms) / Qwen / DeepSeek / TypeSafe  (Provider/Decider seams; ADR-0009, ADR-0042, ADR-0044 decision 7)
```

**One instance, and never locked to one process (ADR-0050).** The box runs exactly one `kajianq-api` process behind nginx, and that stays the posture until measured load says otherwise — but no code may assume it: scalability is architecture principle §18 of [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), so every durable byte lives in Postgres (behind `RagStore`) or the `ObjectStore` seam, the request path carries no client affinity, and an answer is persisted before its SSE stream starts. Adding instances is a deployment change guarded by a closed list — a shared rate-limit counter (today it is per process, ADR-0044), a pinned `max_connections`, an instance-addressable serving path, a single cron owner, and a store-touching readiness probe; a second **host** is a new decision, because Postgres is loopback-only.

The Cloudflare Workers + Neon path this replaces is **removed, not maintained in
parallel** (ADR-0044 decision 2: there are no live users, so the migration is a
single-shot cutover with no rollback runway; the git history is the rollback).
The Neon row's data carried over in one verified transfer, and decommissioning
the old resources is owner-approved (issue #181).

Ingestion and eval harness run as **Bun CLI scripts** (local/CI), never inside the serving runtime, each pointing at `DATABASE_URL`. Deliberate deviation from the template's D1 — the Smart Router needs SQL metadata filtering + pgvector HNSW + tsvector, which D1/Vectorize cannot express.

**Hosting decision (ADR-0043; serving path implemented under ADR-0044; reviewer re-headed 2026-09-21):** the serving path runs on a **netcup GmbH VPS (Germany/EU)** — EU/Germany data residency for chat content and traces (which can reveal religious convictions, Art. 9 GDPR) at VPS cost, with Postgres self-hosted rather than on Neon's free plan (the adapter speaks `pg` over TCP; ADR-0044 decision 5). Because KajianQ serves the public (SPECS §1.1/§2.1), the Art. 2(2)(c) household exception does not apply and a DPA under Art. 28(3) GDPR is mandatory with netcup GmbH as processor (Art. 28(1)); it is concluded in netcup's Customer Control Panel (Master Data → Order Processing) and the sub-processor register, retention values (30-day anonymous sessions per ADR-0017, 14-day access logs, 30-day rolling encrypted backups, superseded snapshot archives deleted 30 days after their successor verifies), and the snapshot personal-data flag live in ADR-0043. The register rule is ADR-0009's, made enforceable: personal data never routes through a vendor's free tier, enforced per call by `personalDataAllowed` filtering in `provider-factory.ts` for any call that declares `PromptSpec.personalData` — **and ADR-0043's recorded gap is closed**: every serving call site (router, generator, reviewer, embedder) now sets `personalData: true` as a required field on its seam type (a compile error to drop), enforced by `apps/api/src/lib/personal-data-serving.test.ts`, and the serving chains carry paid heads (`gemini-paid` for embeddings, `deepseek` for the router/generator and **the reviewer** — #181). **Reviewer re-head (2026-09-21; ADR-0044 decision 7, ADR-0043 decision 3):** the reviewer was designed cross-vendor (`kimi:kimi-k2.6` head, ADR-0009/ADR-0015) but requires a Moonshot key the owner does not hold and elected never to provision; of the held keys only DeepSeek has a `generate`-capable paid candidate (TypeSafe is `decide`-only; free-tier Gemini is refused by the enforcement itself). The reviewer therefore runs `deepseek:deepseek-v4-flash`, **same-vendor review accepted deliberately** — the anti-self-review property is relaxed for the current key set, recorded as a trade-off rather than drifted into, with the revisit trigger "a second paid vendor key is provisioned, then re-head the chain (config only)". The `kimi` vendor row and `MOONSHOT_API_KEY` are removed from `models.json`, `env.ts`, `server.ts`'s `PASSTHROUGH_KEYS`, `api.env.example`, and the runbook preconditions. **Deployment is live on the box:** cutover steps 0–3 executed (hardening applied, Postgres restored, snapshot-verified transfer), and the two ADR-0038 evidence labels are `pre-cutover-20260920t1302` (source Neon, verified before transfer) and `post-cutover-20260920t1316` (target VPS pg 17.11, verified through the loopback-only tunnel) — both manifests report 34,389 rows with equal corpus counts and zero ledger drift. The executed log is [`docs/VPS-CUTOVER-RECORD.md`](docs/VPS-CUTOVER-RECORD.md); the operator's as-is manual is [`docs/VPS-OPERATIONS.md`](docs/VPS-OPERATIONS.md). **Controller-side records (GDPR-B #178):** the Art. 30 record of processing — controller, purposes, data categories, retention, TOMs, sub-processor chain, and the CCP declaration block the owner copies — lives in [`docs/GDPR-ARTICLE-30-RECORD.md`](docs/GDPR-ARTICLE-30-RECORD.md), with the Art. 35 screening and Art. 9 mitigations in [`docs/GDPR-DPIA-LITE.md`](docs/GDPR-DPIA-LITE.md). Both derive from ADR-0043 and restate none of its values; concluding the DPA in the netcup CCP remains the owner's action (#178).

**Provisioning & deploys (ADR-0044; supersedes the Alchemy/Cloudflare serving path):** the deployer is its own concern, outside `apps/` — the build → ship → restart → smoke path is [`provision/vps/deploy/deploy.sh`](provision/vps/deploy/deploy.sh), triggered by the reusable [`.github/workflows/deploy-vps.yml`](.github/workflows/deploy-vps.yml) (Staging calls it, so one implementation exists). `apps/*` carries only app code and build scripts; provisioning stays under `provision/vps/`; CI gates stay in `.github/workflows/`. The script builds two Bun-target bundles from `apps/api/src/boot.ts` (serving) and `apps/api/src/cleanup.ts` (the nightly reclamation), so the box needs no `node_modules`; it ships them with `rsync --delete`, restarts `kajianq-api.service`, runs the cron unit once, and smokes the public URL through the proxy and TLS. Local dev and e2e boot the same Bun entry (`playwright.config.ts`'s webServer), so the tested host is the served host. **The deploy identity is a dedicated account (ADR-0044 decision 6; the 2026-09-21 deploy identity):** `kajianq-deploy`, created by `apply.sh`, owns the deployed tree (so `rsync --delete` needs no group-write grant) and holds exactly two granted commands — `systemctl restart kajianq-api.service` and `systemctl start kajianq-cron.service`, by absolute path and without wildcards — shipped as code in [`provision/vps/sudoers/kajianq-deploy`](provision/vps/sudoers/kajianq-deploy) and installed at `/etc/sudoers.d/` only after `visudo -cf` parses it. Account, grant, and CI's `VPS_USER` are pinned in agreement by `tests/scripts/vps-hardening.test.mjs`, which also fails on an unused grant or a wildcard; the earlier arrangement (deploy as the owner's admin login on a temporary blanket `NOPASSWD:ALL`, documented as three commands but never installed) is what broke the 2026-09-21 deploy. **VPS privacy hardening is provisioned as code (GDPR-D #180):** [`provision/vps/`](provision/vps/) holds the nginx reverse-proxy server block and its minimal access-log format (client IP and request line, no user-agent/referrer/$remote_user), logrotate stanzas for the proxy (14 days total — current day + 13 rotated segments, size-capped, SIGUSR1 reopen) and Postgres (14 days total, `copytruncate`), a journald cap for API logs (14-day / 512M), the loopback-only Postgres posture, the unprivileged `kajianq-api.service` unit, the nightly `kajianq-cron.service`/`.timer` reclamation (ADR-0017's schedule, re-homed by ADR-0044 decision 7), and the `kajianq-backup.service`/`.timer` daily schedule — placed and enabled by `provision/vps/apply.sh` from root-only `/etc/kajianq/*.env` files (which it refuses to source unless root-owned and 0600-or-tighter). ### 3.3 The DARS pipeline (Smart Router)

1. **Intent & Principle detection** (cheap tier) → one JSON payload: `intent (factual|ruling|analogy|comparison|history|aqidah), category, madzhab, grade, textLayer, needsPrinciple, principleTags, confidence, reasoning, subQueries`. **Implemented (#14, ADR-0051):** stages 1 and 2 ride **one** call — a second call would double router latency and cost for information one JSON object already carries — and the domain reads the reply into closed vocabularies, dropping a value outside them rather than force-matching it: `intent` (the six values above), `category` (`quran|hadith|tafsir|fikih|aqidah|tasawuf|sejarah|adab|general`), `principleTags` (`yusr|rahmah|masyaqqah|dharar|umum_balwa|istihsan|sad_zari`), plus the existing madzhab/grade/text-layer filter hints (the caller's explicit filters always win). **One owner for those vocabularies** is the domain pack's taxonomy module, which the router's prompt, the router's narrowing, the Golden Set fixture's labels and the eval CLI's trap marker all read — a test fails when the fixture carries a label the module does not declare, which is how the fixture's `fiqh`/`khilaliyah` spellings were reconciled. The payload lands on the answer's Trace: the classification in the `intent` event (its typed `confidence` and `reasoning` slots, and the category/principle decision/effective filters in its opaque `attributes`), and each sub-query as its own `subquery` event with its role and origin. A reply the vocabularies cannot read — unparseable JSON, or an intent outside the list — takes the recorded **router fallback**: one factual sub-query made of the verbatim question, marked `origin: "fallback"` on the sub-query and `attributes.fallback` on the intent event, with the failed call's cost still on the trace, so the Trace never presents an invented classification as the model's reading. The ticket's `query_type`/`needs_principle`/`principle_tags` are the `intent`/`needsPrinciple`/`principleTags` fields; `subcategory` was dropped (nothing consumed it, and `category` already carries the routing decision), and `grade` joins the filter hints the reply may suggest.
2. **Query decomposition** (cheap tier) → 2–4 **Sub-queries**: always one factual; +principle if `needsPrinciple`; +Quranic dalil if category is fikih; +sanad verification if hadith. **Implemented (#14, ADR-0051):** the model phrases the sub-queries (its paraphrases and classical-term choices are what make retrieval work) and the domain **repairs** the set deterministically — every rule that fired has a sub-query carrying its role — a missing one is added from a template, and where the rule's own text is already in the set under no role of its own (the model echoed the question, or its label fell outside the vocabulary) the rule's role is **stamped onto that entry** rather than a duplicate text being added, with one stated exception: an entry the model itself labelled with a different declared role keeps the model's label, so that rule's coverage is not shown (review R2-A1) — the total is bounded to 2–4 by spending the budget on one sub-query per distinct role before the model's extra angles, and the set is **2–4 whenever two distinct retrieval texts are available** — the caller's question plus either a model sub-query that differs from it or a rule beyond `factual` — but exactly **1** when the only text there is _is_ the question (the model echoed it, or phrased nothing usable), because padding that case would put a synthetic near-duplicate of the question in the Trace and claim a decomposition that never happened (the property suite asserts the contrapositive). Every entry carries its role and its origin (`model`, `rule`, `fallback`) on the persisted trace row, so a repaired route reads as repaired there; the user-visible frame's technical layer projects the intent and each sub-query's **text** only — `ChatTraceFrame.subQueries` stays `string[]`, and `role`/`origin` are read from `answer_traces` (review C1/A2 of the #14 fix round). Retrieval fans out over the set unchanged: one batched embed, a pair of track searches per sub-query, one RRF fuse. **Pending #24:** +Arabic expansion terms from the Terminology Glossary for variant-term queries (ADR-0014; expansion only, never query translation) — no concept-graph reader exists, the router prompt receives no slice, and no expansion candidate is recorded, so the classical terms the model already phrases into a sub-query are the only expansion on the serving path. **Regression evidence (#14):** the ticket's "single-query baseline" was never a shipped state — the router shipped with the chat route itself (#8/#10) — and no ablation switch was added (ADR-0051 rejects one), so the instrument is a **before/after Golden Set run on one deployment**: `bun run eval:run` against staging before and after the change, compared on mean retrieval recall, mean citation validity, refusal counts and per-question flips, with both run ids recorded here by the owner when the runs are executed (the answer prompt is deliberately unchanged by #14, so the comparison is not confounded by prompt wording).
3. **Source routing** (rules + cheap tier) → index selection + SQL metadata filters (`source_type`, `madzhab`, `grade IN …`, `principle_tags ANY …`). **Implemented (#15, ADR-0052; route-wide coverage, #435):** the **rules** decide and the model only hints — the sources the question is answered from are the **union** of what the reply's subject area implies (`quran` → Quran; `hadith` → Hadith; `tafsir` → Quran, its commentary and the Sunnah whose evidence carries a commentary question's "why"; `fikih` → Quran, Sunnah and Kitab, the authority order spent as breadth) and what **every Sub-query's own role** implies (`dalil` and `sanad` → Hadith; `principle` → the Principle Index; `factual` → nothing of its own), derived from the Sub-queries retrieval actually fans out over (repairs and ceiling included), so no part the router decomposed is unsearchable — the base-sha failure was `gs-v0-015`, a `tafsir` route whose own third sub-query asked for the hadith on reciting Al-Fatihah while the filter excluded every hadith row by construction, and the run over-refused; an `analogy` intent or a needed Principle adds the Principle Index; an area no rule covers selects **none** — an unfiltered search already covers every part, so a part's role and the lens rule may widen a selection but never narrow that one back — and the caller's own filters always win. Both maps are exhaustive `Record`s over the vocabularies that own them, so a category or a role added without a source decision is a typecheck failure, and a role the mapping cannot express **fails the run** where it must become a filter, in the same loud style as an unexpressible filter dimension — a boundary guard for the exported mapping's direct callers rather than a serving state: stage 2's decomposition drops a model label outside the vocabulary before the union reads it, so that part reaches the union role-less and is covered by the category row alone. The decision is typed trace content: the `source_routing` event carries the selected sources and **the exact filter record retrieval is handed**, built by the same mapping the searches use, so the decision the trace publishes and the SQL that runs cannot drift over what the rules decided (a dimension the caller pinned is the one exception: `routeFilters` carries the caller's value verbatim, a caller's own filters always winning, while the event publishes its normalized projection — no wire request parses a `filters` field), and the user-visible Trace frame's technical layer projects it — together with the dimensions the run went on to give up, so a filter the search had already dropped is never displayed as one that ran. The mapping is one **exhaustive** `Record<keyof KajianQFilters, string>` — a dimension added without a store key is a typecheck failure — and every dimension is a **set**, bound as `metadata->>key = ANY($n::text[])` (a one-value dimension is a one-element set; there is no second, single-valued spelling). A dimension the store cannot express — an unknown key, the spec's own `source_type` snake_case near-miss included, or a value that is not a list of non-empty strings — **fails the run** at the stage that decided it rather than being dropped: a silently-ignored filter answers a different question than the router chose. The `principleTags` dimension is decidable before the Principle Index (#16) exists, and the text-layer dimension before any kitab is ingested: a tag or layer filter that matches nothing is **probed** — each probe omits one dimension and is recorded with the record it ran with, the hits it returned and whether it was adopted — and only an adopted drop is kept for the run, so `intended − every adopted drop` is the record any search ran with. A sweep that adopts nothing — two unsatisfiable dimensions at once, which is the expected state until the Principle Index (#16) and the kitab ingestion land — ends in **one** record-level retry with `{}`, recorded as an adopted drop of the whole surviving record, so a wrong hint cannot turn into a refusal for a question the corpus can serve; the `adopted: false` probes stay on the trace as the evidence that no single dimension was at fault. The pre-#15 relaxation emptied the whole filter record on the first zero-hit search, which cost a grade screen together with the wrong hint and could not say which hint was at fault. One diagnosis per run, the hints being a property of the request rather than of one sub-query's embedding. **Not yet exercised end to end:** no corpus row carries a `madzhab`, `textLayer` or `principleTags` key, and no `principle`/`kitab`/`tafsir` row exists, so on today's corpus the source and madzhab selections are satisfiable but unobservable, the layer/tag hints probe away, and the evidence is Quran + hadith only — the filters are proved by unit tests and the store's own SQL tests, not by a live route.
4. **Retrieval** — hybrid: pgvector HNSW dense + tsvector sparse (upgrade to ParadeDB `pg_search` true BM25 if the server offers it) fused with **RRF (k=60)** + hierarchy bonuses (Quran +0.3, Sahih +0.25, Hasan +0.15, Kitab +0.1, Principle +0.2 on analogy). **Implemented (#15, ADR-0052):** all five are applied. Four are properties of the chunk — Quran, the two trustworthy hadith grades, Kitab; the fifth is a property of the **question**: a Principle chunk takes its +0.2 only when the route read `intent: "analogy"`, because a Principle is the evidence of an analogy and on a factual question the same chunk is commentary that must not outrank a direct dalil. A weak grade takes nothing: dhaif is flagged, never boosted. Because the bonus depends on the reading, the fuse is handed the intent the route decided (an opaque label — the engine and the arithmetic name no intent). **Surah-reference scoped expansion (ADR-0045, #142/#241):** when the verbatim question names a surah (or a verse in one), the fusion is followed by a deterministic, bounded read of that surah parent's children — `listDocChildrenByParentSourceKey` — added _alongside_ the fused hits, because a short formulaic verse (`QS. 1:1`) is an unreachable semantic neighbour of a whole-surah meta-question (dense rank 929/8,305) and the router's sub-query paraphrase used to flip even the reachable verses in and out of the set. Detection runs on the verbatim question (`RoutedQuery.sourceText`), never on a sub-query; the window is capped by `SCOPE_EXPANSION_CAP` (default 12) and truncated at the parent's opening `ordinal`; an explicit address's verse is kept only when the surah has it (the domain pack's 114 Tanzil ayah counts, so no trace ever names a phantom verse), and the one-word marker-gated spellings (`surat Yasin`, `surat Thaha`, `surat Yaa Siin`) are matched while a bare name still is not. The path is visible end-to-end: the typed `scope_expansion` trace event plus each added chunk ref's `origin: "scope_expansion"`, the user-facing Trace frame's technical layer (which projects that origin label — #243 A1), and the eval outcome's per-question `expansion` block (#243 C1, §3.7) (see §8 `adr/0045`). **Retrieved-verse neighbourhood expansion (ADR-0049, #274):** the same deterministic read is extended to a second anchor — "a retrieved chunk is a verse" — so the verses immediately around the ones retrieval returned join the context too. A verse is anchored on its **stored row**, addressed by the child id the retriever already holds (`RagStore.listDocChildNeighboursByChildIds(anchorIds, { radius, limit })`): the adapter derives the anchor's parent and `ordinal` from that row, returns only its neighbours (never the anchor), deduplicates a neighbour reachable from several anchors onto the **first** anchor, and orders rows by that anchor's position in the caller's array and then by `ordinal` — so a truncated read drops the least important windows and the retriever spends its budget on the best-ranked evidence's neighbourhood. That order is the run's **own retrieval order** — what the `neighbour_expansion` event records — and its determinism limit is recorded in ADR-0049: `rrfFuse` tie-breaks equal scores by chunk id, but the ANN search orders by vector distance alone (a second `ORDER BY` key would cost the HNSW index scan), so ranks among exactly-equal distances can differ between runs. Bounded twice, both read at the composition root: `NEIGHBOUR_EXPANSION_RADIUS` (default 1 — how many ordinals on each side) and `NEIGHBOUR_EXPANSION_CAP` (default 12 — how many chunks may be added); `0` on **either** disables the expansion and a negative value is a typed config failure when the chat wiring builds — the process itself boots green and every `/v1/chat` request answers 503 — never a second spelling of "off" (review R2 of the #274 fix round: the knobs are parsed per request, `chat.ts`'s `wiringOr503`, not at boot); a query whose context holds no verse issues no store read at all. The cap is load-bearing: uncapped, radius 1 would have added a measured p50 of 46 chunks to a Quran-bearing query. Added chunks carry `origin: "verse_neighbours"` (distinct from fused refs and from `scope_expansion`) and the typed `neighbour_expansion` trace event records the anchor ids actually read **in priority order** plus `returned`/`radius`/`cap`/`truncated`, so every added chunk resolves to a read that produced it. **Why:** the generator extends a retrieved verse into a citation **range** (`QS. 3:1-2` written over a retrieved `QS. 3:2`), and the gate — correctly — withholds a citation naming an address nobody retrieved; putting the address in context fixes the cause without weakening the invariant. **The range semantics that go with it (ADR-0049):** a citation that names a list of addresses grounds only when **every** address it names is present. The Quran grammar declares that list (`CitationGrammar.addressesOf`: `QS. 3:1-2` names `QS. 3:1` _and_ `QS. 3:2`), and that list is **every** address the form names — a range's interior included, bounded by the surah's own Tanzil ayah count: `QS. 2:255-260` names all six verses, a multi-dash chain `QS. 3:1-2-3` names 3:1, 3:2 **and** 3:3, and a range whose addresses the surah cannot have (`QS. 2:1-999`) refuses rather than grounding on a shorter reading of itself. The comparison site requires each named address grounded — a range of **one** address included, because a range whose endpoints are equal declares a list of one (`QS. 1:1–1` names `QS. 1:1`, so it grounds exactly when that verse was retrieved; #444) — and the **display** form stays the range as written — so a partially-retrieved range still refuses, head-first and any-member matching stay rejected, and a grammar with no declared list (the hadith number) keeps the whole-label rule #264's A3 trade-off recorded.
5. **Context assembly** — presentation order: Principles → Quran → Hadith → Kitab → concept links; parents contribute LLM summaries so children keep their chapter context. **Implemented (#15, ADR-0052):** the order is one exported constant and its own test pins the whole sequence, not a pairwise comparison — the failure mode is silent, because an assembler that sorted the evidence by _authority_ instead would still produce a coherent, well-cited answer, just one whose lens arrives after the ruling it was meant to frame, and no gate reads the order. The spec's list does not name Tafsir; it is placed immediately after the Quran whose commentary it is, and a source type the order does not name (a concept link, or anything the corpus grows later) sorts **below every named source** rather than being interleaved by score into a slot it was never given. Within a slot the fused score decides; the lens is ordered first because it frames the reading of everything under it, and this order is deliberately distinct from the prompt's authority order — the distinction is the acceptance criterion and the silent failure it guards.
6. **Generation** (quality tier) — strict grounding system prompt (v1.2 §9.5 rules carried over), streaming. **The authority order is stated here (#15, ADR-0052):** rule 8 of the Generator's system prompt carries Quran → Hadith (mutawatir > sahih > hasan; dhaif flagged) → Tafsir → Kitab, in order, in both languages, with the grade precedence inside the rule. It is scoped to what the context already carries ("when the context carries more than one kind of source") so it can never license reaching past the grounding rule above it, and it names the Principle lens as the reading frame rather than as evidence standing on its own. It is _not_ the assembler's presentation order — the two orderings are deliberately distinct — and a test pins each: the prompt's sequence in order, and the assembler's whole layout.
7. **Post-processing** — citation validator (deterministic), grade flags, disclaimer, ID/EN formatting; sampled faithfulness review enqueued. **Implemented (#8):** the five stages live in `packages/kajianq-domain/src/chat-*.ts` and are wired through the `runPipeline` runner by `runChatPipelinePromise`; `/v1/chat` (`apps/api/src/routes/chat.ts`) streams SSE from the first release (ADR-0034). **Citation payload (#11, ADR-0040):** after the deltas, the route emits one structured `citations` frame derived from the just-persisted answer trace — emitted citations are exactly the answer's inline citation spans that a trace-retrieved chunk grounds (the gate's own grammar; the client never parses answer text for citations); the frame's `refusal` flag is a second, independent projection of the same trace — the refusal decision it records — and it never empties that list, so a hybrid answer that quotes grounded verses and then runs into the canonical refusal sentence keeps its chips (#436) — and `GET /v1/chat/sessions/:id/messages` rehydrates a session's transcript with the same per-message derivation from each persisted trace (display data joined by chunk id via `RagStore.getDocChildrenByIds`; traces read by the `answer_trace_id` FK via `getAnswerTraceById`; the transcript is capped at the newest 200 messages and the response's `truncated` flag makes the cap client-visible — thermo-review A4). **Trace panel payload (#12, ADR-0007):** the route also emits one structured `trace` frame after `citations`, and the rehydration endpoint attaches the same frame per assistant message — the two-layer `ChatTraceFrame` (a plain-language `sources` layer first; a `technical` layer with router intent, sub-queries, chunks with their fused scores and channel ranks, and model identities) derived server-side from the persisted trace, with chunk display titles joined by the trace's own chunk ids. The client renders the frame; it never reconstructs pipeline machinery from raw trace events, and an unresolved chunk row loses its title instead of gaining a fabricated one. **Trace shape (#285):** the persisted trace's event vocabulary is closed and typed (ADR-0007), and it now includes `product_rules` — one event on every path that applies the deterministic product rules, naming the rule ids that appended text (see the product-rules bullet below). The event is trace content for the eval harness and the admin browser; the user-facing `ChatTraceFrame` is unchanged by it.

**Acceptance evidence for #15 (ADR-0052), and what is still owed — owner-run.** Four of the five acceptance criteria are machine-checked in the tree and need no deployment: (1) the metadata filters are applied at retrieval and visible in the Trace — the exhaustive dimension map, the loud failure on an unexpressible dimension, the set-valued binding, the recorded `source_routing` decision and the frame's projection of it are each pinned by unit tests, with the store's own SQL under test beside them; (2) the assembled context follows the presentation order and the system prompt states the authority order — one test pins the whole presentation sequence and another the authority sequence, in both languages, plus the scoping that keeps the order from licensing outside knowledge; (4) stage latency and cost are on the trace per query — the runner stamps its own wall clock on the three deterministic boundary events it emits (`intent`, `retrieval`, `assembly`), and every model call carries model identity, tokens, latency and cost on its `llm_call` event, which is where the generator's and the reviewer's latency rides (neither emits a boundary event, and no variant nothing stamps declares a duration); (5) the RRF fusion applies all five hierarchy bonuses — pinned behaviourally, by the ranking flip the Principle bonus causes on an analogy and only there. **Criterion (3) — the Golden Set questions requiring cross-source answers pass on staging — was NOT executed here and stays unticked.** It needs the staging secrets and the §2.8 tunnel, neither available to the implementing agent, and a measurement not made is never claimed. What is owed, by the owner: `bun run eval:run` against staging over the Golden Set and a recorded run id, read on the fixture's only two cross-source questions, `gs-v0-010` and `gs-v0-015` (both `expectedSourceTypes: ["quran", "hadith"]`; `gs-v0-002` and `gs-v0-018` declare a **single** expected source type, so they are usable only as single-source controls that a `sourceType` restriction must not break). The instrument is the harness's `retrievalRecall` over each question's `expectedSourceTypes`: the share of those expected types present among the retrieved refs, which is 1.000 or 0.000 on a single-source question and a genuine both-sources-reached test only on a cross-source one. `eval:run` prints the run's **mean** retrieval recall, with per-question lines only for scoped, failed or skipped questions — so the owed per-question figures are read from the named questions' `eval_results` rows of the recorded run id, not from a CLI line. Two limits make that run a first observation rather than a regression check, and both are recorded rather than papered over: the corpus carries no `madzhab`, `textLayer` or `principleTags` metadata key and no `principle`/`kitab`/`tafsir` row, so on today's data the source and madzhab selections are satisfiable but unobservable and the layer/tag hints probe away on every question that carries them; and no pre-#15 baseline run exists for #15 to compare against, so the owed evidence is an absolute result, not a before/after delta. **Route-wide coverage changes what that owed run measures (#435), in two directions.** The recall it gains: the `gs-v0-015` route's own hadith part now puts `hadith` in the filter, and the `tafsir` row carries it whether or not a part says so, so the hadith leg that was unreachable by construction becomes reachable and the first observation reads the widened rule rather than the base-sha one — `retrievalRecall` is one dimension it moves, because the harness scores the retrieved chunks' `sourceType`s and never reads the `source_routing` event. The displacement it risks: the widened array grows each search's candidate pool, while the store still returns its top `limit` rows per (track, sub-query) (default 10, `packages/kajianq-domain/src/chat-retriever.ts`) and the assembler adds no cap, so a newly admitted `hadith` row can push a previously returned `quran` chunk out of the window — and `citationValidity` reads that same chunk set (`packages/eval/src/harness.ts`: `passed = correct && citations === 1 && recall === 1`), so the required verse of a question can go with it. Two fixture questions are exposed and are the falsification probes for it: `gs-v0-001` (requires `QS. 2:255`; the question names no surah, so ADR-0045's scope expansion cannot fire) and `gs-v0-009` (requires `QS. 89:28`; `DEFAULT_SCOPE_EXPANSION_CAP = 12` keeps the first 12 of QS. 89's 30 verses, so 89:28 lies outside the window — `gs-v0-014`'s `QS. 98:5` is inside its surah's 8). Neither direction is claimed as measured here; the merge-time smoke is what shows both.
**Implemented (#10) — the answer path is complete and its trust invariant is enforced:**

- **Citations are validated on 100% of answers, deterministically, and a fabricated citation is refused.** The validator (`chat-citation-validator.ts`) scans the answer for the product's citation _grammars_ (`QS.`/`Q.S.`/dot-less `QS` `n:n`, `HR.`/dot-less `HR` `<collection> no. n` — multi-token collection forms like `Sunan Abu Dawud` included, Kitab `Jilid n, Hal. n`) in prose and in brackets, and reports any span that exists in no retrieved chunk. Label normalization canonicalizes the dotted `Q.S.` spelling to `QS.`, so a grounded address written that way is not falsely refused while a fabricated `Q.S. 9:99` is still caught. The reviewer turns a non-empty ungrounded list into the plain refusal and records a `refusal` event with `trigger: "ungrounded_citation"`; the cross-vendor reviewer LLM runs only after that gate passes and can add a second refusal (`verdict: "fail"`), and its `review` event carries the grounded labels plus `verdictParseFailed` when the reply held no readable verdict (an indeterminate review is counted, never silently read as a pass). A citation written with a surah _name_ (`QS. Al-Baqarah:255`) is unverifiable against the corpus's numeric labels and is therefore refused, not waved through.
- **Grounding also excludes interpretation the evidence does not carry.** The generator's strict-grounding prompt answers only from the retrieved context and explicitly forbids adding tafsir, takwil, scholarly opinion, or meaning glosses that the context does not contain — including ones the model knows to be correct. A recognised classical opinion is still an ungrounded claim when the retrieved chunks do not carry it, and the trace cannot show where it came from: in the live smoke (`gs-v0-001`) the generator glossed _"Kursi = (ilmu dan kekuasaan-Nya)"_ from memory, the reviewer failed the draft, and the answer became the plain refusal — the gate working as designed.
- **A demanded-but-absent fact is refused, not explained.** When a question asks for one specific fact (a year, date, number, or name) the context does not state, the generator emits the canonical refusal sentence rather than a grounded explanation that the fact is unknown. The refusal is a **product string**, and refusal detection reads that exact sentence (or a trace `refusal` event) — a well-cited "no one knows, here is the dalil" answer is grounded but is not a refusal, so a question like `gs-v0-019` ("state the exact year") would silently flip between pass and fail on the model's phrasing. Naming the shape in the prompt is what makes the refusal case deterministic; the alternative — a paraphrase-tolerant detector — reintroduces exactly the ambiguity the canonical string exists to remove. **The GATE no longer depends on that prose (ADR-0046, #250, 2026-09-28):** a `refuse` question is accepted on a refusal **or** a grounded answer, so a grounded decline in the model's own words passes while a non-refusal with no verified citation still fails. The runtime mandate above is unchanged — it protects users, not the grader — and the prohibition on asserting a date is now prompt-enforced only (a grounded-but-dated answer passes, the accepted residual in ADR-0046). **The reviewer gate is the symmetric backstop (2026-09-13, owner-decided after the c7e20a7 Staging failure):** the generator can disobey rule 1 — in that run it produced a grounded, answer-form "no date is stated; only Allah knows" draft that asserted nothing unsupported, so the reviewer passed it, no `refusal` event was recorded, and the refusal-coverage trap failed. The reviewer's Fail ONLY criteria therefore now include **"declines to answer"**: a draft that, for a question demanding one specific fact the evidence lacks, merely describes, explains, or contextualizes what the evidence does or does not say about it FAILS and lands on a refusal (the reviewer-refusal copy, not the generator's canonical insufficiency string). The case is scoped to that decline-to-answer pattern — partial answers and imprecise wording stay passes — and the anti-over-fail guarantees (translation/quoting/citation labels are required behavior; a term the question itself uses is not an unsupported claim) are unchanged, so the gate cannot start inflating refusals on legitimate answers.
- **The reviewer is non-optional on the chat path.** `buildChatWiring` raises a typed config failure when the reviewer role has no keyed candidate, and the route answers 503 — an unreviewed answer is an unverified one, not a lesser one.
- **The reviewer is shown exactly the Generator's evidence.** `buildReviewMessages` passes the assembler's own context turn — the text the Generator answered from — plus the question, so the gate cannot fail an answer for quoting what the prompt provided. Re-rendering the chunks separately had hidden a fallback-track hit's Arabic from the reviewer (its `chunk.text` is the translation layer), which failed a grounded answer as "the Arabic is absent from the evidence" (gs-v0-015); the question rides along so the gate can tell the user's own term from a claim the evidence lacks.
- **Streaming is real but gated.** The generator calls `Provider.stream` (`StreamHandle`) and the route replays the vendor's own delta sequence on the wire; deltas are emitted only after the reviewer validated the _complete_ answer, so an ungrounded citation is never a prefix already delivered to the user. The cost of this choice is time-to-first-token; for a product whose #1 stated risk is hallucinated religious content it is the correct side of the trade. SSE `data:` payloads are emitted one line per line, so an answer containing blank lines (the appended disclaimer, the dhaif warning) survives the frame boundary.
- **Follow-up context.** `POST /v1/chat` loads the session's prior turns (`RagStore.getChatMessages`) _before_ persisting the new question and passes them on `Query.history`; the assembler renders them as a preamble ahead of the evidence. The engine carries history opaquely (ADR-0018).
- **One question is bounded by the contract, not only by the proxy (#256).** `ChatRequestSchema.message` carries `maxLength(2000)` (`CHAT_MESSAGE_MAX_LENGTH`), and an over-length body leaves through the route's **existing** `400 invalid_request` shape — before auth, the store, or any pipeline stage, so an over-length question spends nothing (pinned by a route test that counts calls on the router/generator/reviewer/embedder seams and asserts none ran, plus no persisted message and no trace). The ceiling is a cost bound, not a UX nicety: ADR-0041's limiter meters request **frequency**, never size, so few-and-huge questions stay inside the rate limit while multiplying what each one spends — and a message is the cheapest lever on router + generator + reviewer spend. It is sized against the product's real questions rather than guessed (the longest curated Golden Set question is 93 characters, the median 55, so 2,000 is ~21× the longest real question — generous for a pasted passage plus a question — while cutting the observed 20,000-character probe by an order of magnitude), the value is an **owner decision** recorded in the issue (adjusting it is a one-line contract edit plus the boundary test that pins it), and it is published on `/openapi.json` (`maxLength` plus a description naming the 400 and the length rule), which the API's own document test asserts. Length is measured in UTF-16 code units on the **raw** string — nothing in the request path trims, so a body that would only trim to 2,000 is still rejected, while a whitespace-only body inside the ceiling is accepted (the composer trims, so the UI cannot build one; the boundary tests pin both halves). The composer mirrors the ceiling — the field's `maxLength`, a clamped draft (the attribute alone does not constrain a programmatically set value), and an externalized en/id hint at the limit, so a reader never meets an unexplained 400 — and the `?q=` prefill cap (#175, 200) stays under it by test.
- **A session id the store cannot hold is refused at the boundary, not by the store (#271).** `ChatRequestSchema.sessionId` validates through the shared `ChatSessionIdSchema` (`uuid` — `chat_sessions.id` is a Postgres `uuid` column and every id the API mints is `crypto.randomUUID()`), so the QA finding's body (`{"message": …, "sessionId": "en"}`) leaves through the route's **existing** `400 invalid_request` before auth, the store, or any pipeline stage. Before this, the same body passed validation and died in the adapter's `${sessionId}::uuid` cast as `500 {"error":"internal"}` — no SSE frame, no trace id, a bare server-fault shape for a malformed field. The rule is published on `/openapi.json` (`format: uuid` plus a description naming the 400 and the 404), which the API's own document test asserts, and the refusal's logged diagnostic now names the offending field (valibot's `path` holds PathItem objects; joining them raw printed `[object Object]` for every rejected body, not only this one). The rendering lives **once**, as `describeIssue` in `@app/contracts` — `issuePath` renders the path, `describeIssue` is the single `field: message` template over it, and a path-less `v.union` issue is resolved through its nested `issues` to the deepest one that names a field (so the feedback union's `rating: "meh"` reads `rating: …`, not `<body>: …`) — shared by the chat and feedback body parsers (#283, whose 400 keeps its `{"error":"invalid_request"}` body and pins the field-naming with its own rows, field-level and union) and by the eval fixture loaders — so no route can regrow a second copy that prints `[object Object]` or leaves a union failure field-less. The check is a **format** check only: a well-formed but unknown or foreign UUID answers exactly what it answered before, so it cannot become an existence oracle — the route tests pin the unknown and foreign cases to one shared status and body. The sibling seam is guarded the same way: `GET /v1/chat/sessions/:id/messages` has no body schema in front of `c.req.param("id")`, so a malformed `:id` there now answers the route's documented `404` (same body as unknown/foreign) instead of the 500 the same cast produced; auth still runs first (a malformed id without a token is 401), and no status was added to that route's published contract. The two server-produced `sessionId` members (`ChatMetaSchema`, `ChatSessionMessagesSchema`) deliberately keep the opaque `minLength(1)` form: their values come from the store, the `RagStore` seam types chat session ids as `string`, and a response schema claiming a UUID shape would over-constrain every adapter while preventing no 500 — a response assertion is not a boundary (the contract tests pin that decision rather than leaving it to prose). BDD covers the user-facing half: a stored session id the server cannot represent rehydrates as the documented 404, the page starts a fresh chat with no error, and the malformed id is cleared rather than replayed into a 400.
- **Product rules are deterministic, not prompt-hoped** (spec §2.2 "Grade flag — Always"): `chat-postprocess.ts` appends the dhaif warning when a retrieved chunk carries grade `dhaif`, the ADR-0006 machine-translation label when the context held a labeled translation the answer dropped, and the not-a-fatwa/consult-ulama disclaimer when the answer omitted it. Never duplicated, and never applied to a **pure refusal** — a classified refusal that cites nothing (round-3 A2): the reviewer short-circuits it before any rule runs, records a `refusal` trace event (`trigger: "generator_refusal"`), pays no reviewer LLM call, and ships it verbatim, inventing no warning for a text that cites no weak evidence. **That classification may skip the paid reviewer; it may not skip a rule the spec marks Always (#439):** a **hybrid refusal** — the same canonical sentence riding a grounded partial answer, whose grounded chips the citations frame keeps beside the flag (#436) — is answer content, so it funnels through `applyProductRules` exactly as the reviewer-passed path does: the grade flag and the disclaimer are computed for the text that actually ships, and the `product_rules` event recorded beside the `refusal` event is what makes that visible on the trace, while the paid reviewer is still skipped (ADR-0009). The dhaif-warning suppression anchors to the product-owned warning copy alone (round-3 B4 tightened it from a proximity window; #278 tightened it off the bare token): the evidence renders every weak-grade chunk's label as `(Dhaif)`, so an answer whose context carries a dhaif chunk contains the term for a reason that is not a warning, and matching it silenced the control on its whole target set. The same predicate (`hasWeakWarning`) is what the citations frame's `dhaifWarning` flag reports, so the delivered answer and the frame cannot disagree. The assembler renders the Arabic original with the labeled translation per chunk — the retriever carries both text layers into the chunk metadata, so the rule is live on the real path, not only on fixtures — and the model never reproduces Arabic from memory. **Which rules appended text is trace content, not an inference from the answer (#285):** `applyProductRules`'s `applied` list is recorded as one typed `product_rules` event on every path that applies the rules — the no-provider/`skipLlm` exit, the ADR-0042 pre-gate skip (which records no `review` event at all), the reviewer-passed exit, and the hybrid-refusal exit (#439) — and an empty `applied` says the rules ran and appended nothing — it does not separate "no rule had a trigger" from "a trigger matched and the copy was already present" (the exact-copy suppression case that motivated the event), and the delivered text alone cannot distinguish either from "the rules never ran". A run with `applyProductRules: false` (test/eval refusal wirings) records no event, because the event means "the rules ran", never "the stage passed"; the event names only which rules appended text and never what the answer says.
- **Anonymous sessions (ADR-0017) are mounted:** `POST /v1/auth/anonymous` mints a 30-day Bearer session through `RagStore.createSession`; `DELETE /v1/auth/me` erases the user and their subtree (sessions, chat sessions/messages, feedback, answer traces) via the cascade. Both auth routes wire the **store only** (`buildStoreWiring`) — auth availability is not coupled to any LLM role, so a missing reviewer key cannot take down token minting or the erasure right. A nightly systemd timer (`kajianq-cron.{service,timer}`, `provision/vps/systemd/`, at ADR-0017's 03:17 UTC slot) runs `apps/api/src/cleanup.ts`, which calls `ragStore.cleanupExpiredSessions()` — reclaiming the expired `sessions` rows **and** the anonymous `users` left with no session (the FK cascades user → session only, so users and their chat/trace subtrees would otherwise grow without bound); the entry is inert without a configured store, logs the settled result, and logs rather than throwing on a store fault. ADR-0044 decision 7 re-homed it from the Worker's cron trigger so the schedule stays independently observable and reclaims even when the serving process is unhealthy.
- **Golden Set smoke subset:** `bun run eval:smoke` runs a deterministic, stratified slice (refusal, trap, English, Indonesian coverage first, then stable-order fill — `packages/eval/src/smoke-subset.ts`) through the same harness and ledger as `eval:run`, and applies the same exit policy `eval:run` does (#364): non-zero on any failed question, any skipped question, or any question the run never measured — a truncated run records fewer outcomes than the set it was asked for, which is how a budget-capped run reads, because the harness stops the loop on the cap without counting the remainder (`exitPolicy`, `packages/eval/scripts/eval-cli.mjs`). The gate fails on a skip as it does on a failure because **an unmeasured question is not a pass** — "we could not ask" must redden exactly as loudly as "we asked and the answer was wrong", or a transport outage would buy a green release — and the skip's cause is never the exit code alone: the harness persists the skipped question as its own `eval_results` row (`skipped: true` with the transport error in `notes`, the same note the run report carries) and the run summary prints a `skipped: <message>` line, so the store, the report and the CI log agree on the cause (#290). A live run needs staging secrets (`EVAL_API_BASE_URL`, `EVAL_API_TOKEN`, `DATABASE_URL` — vendor-free since ADR-0044, vendor keys); the selector is unit-tested, the live run is not part of CI.

Question wording lives in the domain pack (the same language-neutral citation question the gate benchmarked) and reaches the engine as opaque template data. **The embedding default is gate-decided (ADR-0036, 2026-09-10); the serving row is the paid-terms one (#181).** Per ADR-0013 (accepted), retrieval is Arabic-canonical: `text_ar`/`embedding_ar` is the primary evidence index; `text_id`/`embedding_id` is a built-from-the-start fallback/fusion track. The #9 benchmark gate compared `gemini-embedding-001` and `gemini-embedding-2` on ID→AR and AR→AR recall over the real corpus (self-retrieval probes, cosine recall@10) plus the ADR-0014 expansion micro-task; the floors are the harness's contract (`GATE_FLOORS` in `packages/eval/src/embed-bench.ts`), the decided retrieval posture is recorded in `adr/0036-embedding-benchmark-gate-retrieval-posture.md`, and the numbers live in the run report (`packages/kajianq-domain/fixtures/embed-bench-results.json`). ### 3.7 Integration testing (real, per notes.md)

- **Golden Set**: ~50–100 ID/EN questions with expected source types, required citations, known traps (dhaif hadith, cross-madzhab differences, untranslated kitab, refusal cases). **Implemented (#8):** `golden-set-v0` — 20 questions (17 ID, 2 refusal, 1 dhaif trap), Quran+hadith scope only until kitab ingestion lands; fixture at `packages/kajianq-domain/fixtures/golden-set-v0.json`, `status: "v0-draft"` until the owner signs the content off (the #8 curation gate is `model:plus-human`). A `requiredCitations` label must be reachable in the corpus the gate runs against: re-curating one because retrieval provably cannot surface it is a recorded curation change (fixture `$comment` + the linked recall issue), never a silent re-label. The first such change moved `gs-v0-015` from `QS. 1:1` (dense rank 929/8,305 for the best live sub-query — see #142) to `QS. 1:2`.
- **Metrics**: retrieval recall, citation validity (deterministic), faithfulness (LLM judge). **Implemented (#8):** recall is scored from the served pipeline's persisted answer trace (`retrieval` events), citation validity and refusal correctness are deterministic; the judge role is wired as the pipeline reviewer (**same-vendor since 2026-09-21 — the judge's vendor separation is relaxed, §3.4**), and a standalone faithfulness judge over golden answers remains a later step. See ADR-0034. Citation validity reads its evidence in a fixed order — the SSE `citations` frame (ADR-0040) when the transport carries one, else the trace `review` event's `grounded` labels, else the answer text through the citation gate's own grammar (`citationCandidatesIn` + `normalizeCitationLabel`, injected by the CLI composition root so the engine package stays domain-agnostic) — so a label in a non-empty frame is grounded by construction and a fabricated citation still cannot pass, and the text path no longer scores a grounded marker-spelling variant (`Q.S.`/`QS ` for the fixture's `QS.`) as absent. **A hybrid refusal is scored on the citations its text actually carries (#436):** a generator-emitted refusal can be the tail of an answer that quotes retrieved verses, so the frame is the cited-and-grounded intersection with no refusal case and `citationValidity` reads those grounded labels instead of 0, while the refusal dimension is unchanged — it reads the trace's `refusal` event, so an `answer` question a hybrid draft answered is still scored as an over-refusal. This is necessary but **not sufficient** for `gs-v0-015`: the observed staging failure (`eval_runs` run `e0de2bf8-5ad6-4618-a0ae-4a96343aabac`, 2026-09-19) retrieved zero Al-Fatihah chunks, so the frame itself was empty and the answer cited only its hadith evidence — a retrieval gap, not a scorer defect, owned by #142 ("short formulaic verses unreachable for whole-surah questions"). **Addressed by ADR-0045 (2026-09-27):** a question naming a surah now retrieves that surah's children deterministically (bounded by `SCOPE_EXPANSION_CAP`), so `gs-v0-015` no longer depends on the router's sub-query wording; #241's flake is closed for observation only after `main` shows it stable, which is the manager's call. **What the ADR-0045 gate measures, made visible (#243 C1):** the scorer reads the retrieval event's chunk refs and never inspects their `origin`, so for the four reference-naming questions (`gs-v0-005`/`009`/`014`/`015`) the scored leg is satisfied by construction whenever the scoped read works — and the harness records that per question, deterministically and with no judge: each outcome persists `expansion.chunks` (how many refs the **scope** expansion added) and `expansion.fusedOnlyRetrievalRecall` (the recall of the refs that carry **no** `origin` label — every deterministic expansion path labels its own chunks, so the fused-only leg excludes ADR-0049's `verse_neighbours` chunks too and a future expansion cannot silently inflate it), and the CLI summary prints a `scoped:` line per such question. **Where that visibility stops is itself recorded (review R6 of the #274 fix round):** the `expansion` block is emitted only when the **scope** path ran, so a question the ADR-0049 neighbour path carried has no `expansion` block in its outcome — its contribution is on the persisted trace (`neighbour_expansion` plus each ref's `origin: "verse_neighbours"`) rather than beside the reported recall, and a fused-track regression on such a question is read from the trace, not from `eval_runs.report`. A fused-only figure below the reported one is the report's own statement that the expansion carried the question, so a fused-Quran regression on those four is visible in `eval_runs.report` rather than folded into a 1.000 mean; the metric itself is unchanged, and the other sixteen questions still measure the fused path (with `citationValidity` still binding verse-specific requirements). **Trap acceptance (ADR-0046, #250):** for an `expectedBehavior: "refuse"` question the behavior dimension accepts a **refusal** or a **grounded answer** — one carrying at least one citation the existing evidence verifies (the citations frame first, else the trace `review` event's `grounded` labels, with no answer-text fallback, so a fabricated citation cannot ground itself). **Range citations are checked per address (ADR-0049, #274):** the Quran grammar declares that a dash-joined range **names** every address in it — interior included, bounded by the surah's own Tanzil ayah count — so `QS. 3:1-2` is grounded exactly when the retrieved context holds `QS. 3:1` and `QS. 3:2`, `QS. 2:255-260` needs all six of its verses, `QS. 3:1-2-3` names 3:1, 3:2 and 3:3, and each is still refused when any named address (or an impossible one, `QS. 2:1-999`) was not retrieved; the **spaced** spelling names the same list and gets the same verdict, and a range the grammar cannot enumerate at all (`QS. 2:1-999`, `QS. 2:255 - 0`, a tail in another script's digits) refuses in **both** spellings — the fail-closed case is a third state of the declaration (`addressesNamedBy` returns `null` for "declared and unenumerable", never a one-element list, which is indistinguishable from "this grammar declares a single address"; review T1 of the #274 fix round) — strictly tighter than head-first or any-member matching, and the completion of the follow-up #264 recorded at the comparison site. **A declared list of one is decided as a list (#444):** `QS. 1:1–1` names exactly `QS. 1:1`, so it grounds exactly when that verse was retrieved — read off the declaration, not off the list's length, because the old `named.length > 1` test sent the span to the shortened-label rule, which needs `<label>` + a space and refused a verifiable citation (on staging that refusal replaced a 31-chunk grounded answer with the canonical one). A range of one the surah cannot hold (`QS. 2:0-0`, `QS. 2:999–999`) or one written with a surah name still refuses. The candidate label itself is unchanged (whole range), so the refusal reason, the reviewer pre-gate's claim span and the citation the user reads still name what the draft named; a grammar that declares no address list keeps the whole-label rule. A non-refusal with **no** verified citation still fails, which is what keeps `gs-v0-019` (no required citations, no expected sources) a live gate rather than a question that cannot fail; an `answer` question that is refused still fails (over-refusal is a defect), and the rule is general over every `refuse` question — no per-question vocabulary, acceptance block, or detector. The evidence-supply path is **code-verified but not yet observed end-to-end** (every test hands the frame in as a literal, ADR-0046), so #250 — like #241 — is closed for observation only after the staging smoke for the merge commit shows `gs-v0-019` passing, which is the manager's call. **The prohibition on asserting a demanded-but-absent date is prompt-enforced only:** a grounded-but-dated answer passes the gate, an accepted residual recorded in ADR-0046.
- **Cadence (decided in #359, owner decision 2026-10-03):** the eval gate is the cost-capped 5–10 query smoke on every code-bearing staging deploy, not in the PR gate set (see the "Where the smoke runs" bullet below); the full suite is operator-invoked at the documented release gate, and it exits non-zero on any failed, skipped, or unmeasured question (#364) — the same shared policy the smoke applies. **No nightly run, and none is planned** — a nightly would re-measure, on a schedule, the commit the merge gate already measured, at real vendor prices. Cost-capped; results in admin. Template's unit/property/BDD gates remain unchanged. **Implemented (#8):** `bun run eval:run` (`packages/eval/scripts/eval-run.mjs`) — hard `EVAL_BUDGET_MICRO_USD` cap covering harness + pipeline spend, per-question rows in `eval_results`, aggregate `EvalRunReport` in `eval_runs`. **Implemented (#10):** `bun run eval:smoke` runs the 5-question smoke subset (`EVAL_SMOKE_SIZE` overrides) selected by `packages/eval/src/smoke-subset.ts` — stratified so a refusal case, a trap case, an English case, and an Indonesian answer case are always present before the budget fills by stable order; it applies the same shared exit policy (#364), so CI can gate on it — a skip fails the gate because an unmeasured question is not a pass, and its cause is persisted per question (`eval_results.outcome.skipped` plus the `notes` message) and printed in the run summary (#290). A **scored** failure is attributed in the same block: one `failed: <questionId> …` line per failed question, naming every dimension that missed its rule with the evidence behind it — `retrievalRecall` with the question's expected source types and how many were retrieved, `citationValidity` with its required citations and how many were present, and the behavior rule where the outcome decides it (an `answer` question refused; a `refuse` question answered without a verified citation) — read from the in-memory outcomes and the already-loaded fixture, never a store read, so "which question, which dimension" is answered by the CI log itself (#340). **The issue-level companion is the QA phase (#252):** the smoke is the scheduled floor on five questions, and a manager-classified **runtime** change additionally gets adversarial staging verification of the issue's own observable — the shapes, the ticket brief, and the probe taxonomy are the §2.2 row and the `qa-phase` skill's contract; a QA-needed change is not finished until a `verified` / `not verified` / `blocked` verdict is recorded, and `ship`'s completion criterion carries the same requirement. QA rides the smoke's **$1 per run** cap (ADR-0034), itself a **recorded** bound over the same ~1000x-low `costMicroUsd` whose calibration is #296 — probe discipline (the smallest set that proves the observable and its blast radius) is what bounds real spend until then.
- **Where the smoke runs (2026-09-12; split into its own job 2026-09-14):** in the `Staging` workflow's `post deploy checks` job, which runs after every staging deploy — a push/merge outside `paths-ignore` and an operator dispatch; that deployment is the one deployment, and `staging` is its environment label (no production is provisioned, ADR-0044 decision 2; deferred 2026-10-03) — not in the PR gate set. Docs-only or tests-only pushes (markdown anywhere, `docs/`, `adr/`, `NOTICES/`, `.agents/`, `.zcode/`; the whole `tests/` tree including its features, steps and fixtures, plus `*.test.ts`/`*.test.mjs` suites and the test-support class — whose membership is stated once, at the patterns themselves in `.github/workflows/staging.yml`, never as a second list here — under the invariant that a file whose whole purpose is test support is never imported by production code — enforced, since #399, by `scripts/check-paths-ignore-invariant.mjs` in `bun run lint`: it parses those patterns, matches them over `git ls-files` with GitHub's glob semantics, and fails when a matched path is in the static import closure of the four `provision/vps/deploy/deploy.sh` entries, refusing rather than passing whenever it cannot read the trigger) cannot change the deployed site, so they skip the push trigger (`paths-ignore`, skipped only when _every_ changed file matches) — a deploy plus its paid smoke would be pure spend with no new artifact to verify; an operator dispatch always remains available. The workflow's `deploy` job guards the secrets (including the chat pipeline's vendor keys) before deploying; the `post deploy checks` job then mints its own anonymous session (`POST /v1/auth/anonymous`, ADR-0017) and runs `bun run eval:smoke` against the deployed site with `EVAL_BUDGET_MICRO_USD` always set ($1), so a staging deploy that breaks grounded answering or the refusal gate cannot go green — and a failed deploy skips the checks instead of scanning or scoring a stale environment. PR-time smoke against _PR code_ is not possible without deploying a preview, so the deploy-then-smoke pairing is the gate; `EVAL_SMOKE_SIZE`/`EVAL_BUDGET_MICRO_USD` are dispatch inputs.
- **Staging corpus (one-off, 2026-09-12):** the smoke scores retrieval recall from the persisted traces, so staging must hold a real corpus. It is loaded **once per environment** by an operator running the ingest CLIs locally against `DATABASE_URL` (`NEON_DATABASE_URL` at the time; renamed vendor-free by ADR-0044) (`db:up:all` → `ingest:quran` → `ingest:hadith`, one collection per pass via `--offset`/`--limit 1`) and verifying the landed `sourceType` counts. The `Staging` workflow carries **no** ingest job (ADR-0037): a money-spending job must never sit in the same workflow graph as the evidence job, because a failed ingest would then skip the smoke — spending money and producing no evidence, which is exactly what happened on four runs on 2026-09-12. The store persists across deploys the way production's does. Note the ingest CLIs are idempotent in _persistence_ (upserts by `sourceKey` / `(parentId, ordinal)`) but **not** in _cost_: a pass re-embeds every row it reads, so re-running a collection that already landed pays for it again — resumption is by measured store state, never by re-dispatching. Before this, staging held only `neon-contract` fixtures (`ct-…` keys, no `sourceType` metadata) and an empty `eval_runs` — no ingestion report had ever been persisted there. **Scoped for the MVP (ADR-0039, 2026-09-12):** staging deliberately carries only the _smallest corpus that satisfies the gate_ — Quran plus **one** hadith collection (Malik, ~1,829 records / ~56 MB, landing the store at ~291 MB, 58% of Neon's free 0.5 GB cap), because the free plan **fails writes** on overage and the gate scores behaviour rather than corpus coverage. The full corpus (~35,573 hadith children, ≈1.35 GB projected) is a **production milestone** on the production store, not a staging requirement. The smoke's evidence is therefore a behavioural gate on a partial corpus, and a PR citing it must say so. **Production load (2026-09-26, #213):** with the cap gone (ADR-0044) the full corpus — the six remaining hadith collections — is loaded on the VPS store by the same operator discipline, now with the committed `--only-missing` guard (ADR-0037's fired revisit trigger) and bracketed snapshots; the executed sequence and its evidence live in [`docs/CORPUS-INGEST.md`](docs/CORPUS-INGEST.md) §4, and the corpus numbers this spec quotes are re-read from the store in the same PR (see §3.2). **Measured 2026-09-26:** all six collections landed at exactly their declared `--check` counts (bukhari 7,580, muslim 7,360, abudawud 5,272, tirmidhi 3,924, nasai 5,679, ibnmajah 4,338) with Quran and Malik demonstrably untouched — the store holds 42,511 children / 804 parents / 37,014 aligned pairs, 1,431 MB, six snapshot-bracketed passes at 2,838 micro-USD total, every pass `archiveStored: true`.

## 9. v2 Plan — Sanadset: Isnad data & per-chain grades (targeted for v2.0)

### 9.1 Goal

Close v1's integrity gap. v1 stores one flattened grade per matn, but hadith science grades **chains, not texts**: the same matn can be sahih via one isnad and dhaif via another, and weak chains can strengthen each other (hasan li-ghayrihi). A trust-first product cannot stay confidently wrong in this class of answers. v2 makes grades per-chain with grader attribution and shows transmission evidence (ADR-0012).

### 9.2 Scope

- **In:** Sanadset ingestion (650K hadith, tagged sanad/matn); `narrators` + `hadith_chains` tables; reconciliation against the v1 hadith corpus; per-chain grades in citations, answers, UI, and Trace; narrator-reliability answers; Golden Set v2 gate.
- **Out:** full GraphRAG / any graph DB (ADR-0012 — recursive SQL suffices); narrator biographies beyond Sanadset fields; non-hadith chains (e.g., tafsir isnads) — later.

### 9.3 Data layer (additive migration)

- `narrators`: id, canonical_name_ar, name_variants[], kunya, laqab, death_year, tabaqa, per-critic reliability JSONB, metadata.
- `hadith_chains`: id, child_id → doc_children, collection, narrator_ids[] (ordered), grade, grader, source_ref.
- Teacher/student relations derived from chain adjacency — no separate table in v2.
- Existing v1 rows, embeddings, and indexes untouched — no re-ingestion, no re-indexing.

### 9.4 Ingestion (CLI, off-Workers)

Acquire (Kaggle; **human prerequisite: verify license terms**) → parse sanad/matn tags → narrator entity resolution (deterministic Arabic name normalization → LLM assist on unresolved → sampled cross-vendor review; variants recorded) → matn reconciliation (exact → normalized → fuzzy + LLM adjudication; unmatched ingest as new children; low-confidence quarantined, never force-merged) → attach chains; same-matn variants linked via `concept_links` → ingestion report (match rate, resolution rate, quarantine count, cost).

### 9.5 Retrieval, generation, UI

- Retrieval filters: chain grade, narrator.
- Citation: `HR. Bukhari no. N (Sahih — al-Albani; chain via …)`; multiple chains presented neutrally; dhaif flagged as in v1.
- Prompt rules: never upgrade a grade beyond retrieved evidence; note corroboration when chains support it.
- Trace shows chains consulted; takhrij-style answers when cross-collection evidence exists.

### 9.6 Eval & gate

Golden Set v2 traps (ID/EN): conflicting grades per matn; corroboration cases; narrator reliability; takhrij. Cross-vendor faithfulness judge validates per-chain claims against retrieved chains. v1 suite must stay green. Full gate before v2.0.
